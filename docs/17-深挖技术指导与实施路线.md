## 1. 先给结论：这个项目值得继续深挖

你的理解是对的。

这个项目虽然现在很多地方还是简单 CRUD，但它不是一个“没价值的练习项目”。

它已经有了真实商业系统的骨架：

```text
用户
员工
登录
JWT
商品
分类
套餐
购物车
地址
订单
支付模拟
订单状态
报表统计
Redis 缓存
定时任务
WebSocket 通知
文件上传
接口文档
全局异常
分页查询
MyBatis XML
```

这已经比“学生管理系统”“图书管理系统”更接近企业级业务。

你现在最应该做的不是：

```text
再找一个新项目从头写一遍 CRUD。
```

而是：

```text
拿当前项目当训练场，把每个模块从“能跑”升级到“像真实业务一样可靠”。
```

更具体一点，你接下来要做的是：

```text
1. 把报表统计补完，练 SQL 和数据整理。
2. 把下单、套餐、菜品这些多表写入补事务。
3. 把订单状态流转做成真正有规则的状态机。
4. 给接口补参数校验、异常处理、错误码。
5. 把 Redis 缓存从“能用”升级到“有一致性策略”。
6. 优化典型慢查询和 N+1 查询。
7. 补权限和越权检查。
8. 加库存、限购、防重复提交等商业场景。
9. 加测试、日志、部署，让项目能交付。
10. 最后再考虑 MQ 和微服务。
```

这个顺序很重要。

先把单体业务系统打磨好，再引入更复杂的中间件。

## 3. 你接下来不要做什么

### 3.1 不要马上重写项目

不要这样：

```text
这个项目写得不够企业级，我重新开一个。
```

更好的方式是：

```text
保留已有业务，逐步改造。
每次只改一个主题。
每次改完都能运行和验证。
```

真实工作里更多是维护和改造已有项目，而不是每天从零开始。

### 3.2 不要一次性引入一堆技术

不要同时做：

```text
Redis
RabbitMQ
Kafka
Spring Security
Spring Cloud
Docker
Elasticsearch
Seata
```

这样会把学习目标打散。

你现在要按业务问题引入技术：

```text
查询重复、访问频繁 -> Redis
多表写入要一致 -> 事务
状态流转容易乱 -> 状态机
接口参数不可信 -> Bean Validation
订单通知不想同步等 -> 异步 / MQ
服务太大、团队协作困难 -> 微服务
```

### 3.3 不要只追“高级名词”

很多看起来高级的技术，背后都是基本问题。

比如：

```text
缓存一致性 -> 数据库和 Redis 谁先改、失败怎么办
幂等 -> 重复请求不能造成重复业务结果
限流 -> 请求太多时保护系统
削峰 -> 流量高峰先排队慢慢处理
分布式事务 -> 多个服务的数据一致性
```

如果你在单体项目里没理解这些问题，直接学微服务也会浮在表面。

## 5. 第一阶段：先补报表统计，把 SQL 能力拉起来

这是你当前最适合先做的阶段。

原因：

```text
1. 你刚好卡在 group by、聚合函数、ECharts 数据整理。
2. 项目已经有 ReportController、ReportService、ReportMapper。
3. 项目已经有 TurnoverReportVO、OrderReportVO、UserReportVO、SalesTop10ReportVO。
4. 这是从 CRUD 走向业务查询的最佳入口。
```

### 5.1 当前现状

已有：

```text
ReportController:
  /admin/report/turnoverStatistics

ReportService:
  turnoverStatistics(LocalDate begin, LocalDate end)

ReportMapper:
  sumByMap(...)

VO:
  TurnoverReportVO
  OrderReportVO
  UserReportVO
  SalesTop10ReportVO
```

当前重点问题：

```text
营业额 SQL 有雏形，但 Service 还没有把 SQL 结果整理进 turnoverList。
订单统计、用户统计、销量 Top10 还可以继续补。
```

### 5.2 第一小步：补完营业额统计

目标：

```text
GET /admin/report/turnoverStatistics?begin=2026-06-01&end=2026-06-07

返回:
{
  "dateList": "2026-06-01,2026-06-02,...",
  "turnoverList": "120.00,0,88.00,..."
}
```

建议做法：

```text
1. 新建 TurnoverDailyDTO
2. ReportMapper 增加 sumTurnoverByDay
3. ReportMapper.xml 使用 group by date(order_time)
4. ReportServiceImpl 生成完整日期列表
5. SQL 结果转 Map<LocalDate, BigDecimal>
6. 按完整日期列表补 0
```

你要练到的能力：

```text
LocalDate -> LocalDateTime
group by
sum
coalesce
List -> Map
补齐日期
拼接逗号字符串
```

验收标准：

```text
1. 有订单的日期显示真实金额。
2. 没订单的日期显示 0。
3. dateList 和 turnoverList 长度一致。
4. 日期顺序从 begin 到 end。
5. 只统计已完成订单。
```

### 5.3 第二小步：补订单统计

目标接口：

```text
GET /admin/report/ordersStatistics?begin=2026-06-01&end=2026-06-07
```

返回 VO：

```text
OrderReportVO:
  dateList
  orderCountList
  validOrderCountList
  totalOrderCount
  validOrderCount
  orderCompletionRate
```

建议 SQL：

```sql
select
    date(order_time) as orderDate,
    count(*) as orderCount,
    sum(case when status = 5 then 1 else 0 end) as validOrderCount
from orders
where order_time >= #{begin}
  and order_time < #{endExclusive}
group by date(order_time)
order by orderDate
```

你要练到：

```text
case when
按天统计总订单和有效订单
完成率计算
Long 和 Integer 的转换
除数为 0 时避免异常
```

验收标准：

```text
1. 每天订单数正确。
2. 每天有效订单数正确。
3. 总订单数等于每天订单数之和。
4. 有效订单数等于每天有效订单数之和。
5. 没订单时完成率为 0，不报错。
```

### 5.4 第三小步：补用户统计

目标接口：

```text
GET /admin/report/userStatistics?begin=2026-06-01&end=2026-06-07
```

返回 VO：

```text
UserReportVO:
  dateList
  totalUserList
  newUserList
```

建议思路：

```text
1. 查 begin 前已有多少用户。
2. 查 begin 到 end 每天新增多少用户。
3. Java 里逐天累加。
```

你要练到：

```text
count
group by date(create_time)
累计值计算
完整日期补 0
```

验收标准：

```text
1. newUserList 表示每天新增。
2. totalUserList 表示截至当天总用户。
3. totalUserList 应该是递增或不变。
```

### 5.5 第四小步：补销量 Top10

目标接口：

```text
GET /admin/report/top10?begin=2026-06-01&end=2026-06-30
```

返回 VO：

```text
SalesTop10ReportVO:
  nameList
  numberList
```

项目里已经有：

```text
GoodsSalesDTO
OrderDetail
SalesTop10ReportVO
```

建议 SQL：

```sql
select
    od.name as name,
    sum(od.number) as number
from order_detail od
join orders o on od.order_id = o.id
where o.status = 5
  and o.order_time >= #{begin}
  and o.order_time < #{endExclusive}
group by od.name
order by number desc
limit 10
```

你要练到：

```text
join
group by
sum
order by desc
limit
DTO 接收聚合结果
```

验收标准：

```text
1. 只统计已完成订单。
2. 只统计时间范围内订单。
3. 商品按销量倒序。
4. 最多返回 10 个。
```


你现在先把：

## 6. 第二阶段：补事务，把多表写入做可靠

后端业务系统的一个关键能力是：

```text
不是接口能跑，而是数据不能写坏。
```

你项目里有很多多表写入场景，非常适合练事务。

### 6.1 重点场景一：用户下单

当前核心方法：

```text
OrderServiceImpl.submit
```

它做了：

```text
1. 查询地址
2. 查询购物车
3. 插入 orders
4. 插入 order_detail
5. 清空 shopping_cart
6. 返回 OrderSubmitVO
```

这是典型事务场景。

如果出现这种情况：

```text
orders 插入成功，
order_detail 插入失败，
shopping_cart 没清空。
```

数据库就会不一致。

所以这个方法应该重点练：

```java
@Transactional
```

验收方式：

```text
1. 在插入 orders 后故意抛 RuntimeException。
2. 调用下单接口。
3. 检查 orders 是否没有新增。
4. 检查 order_detail 是否没有新增。
5. 检查 shopping_cart 是否没有被清空。
```

你要理解：

```text
事务不是为了代码好看。
事务是为了多步数据库操作要么都成功，要么都失败。
```

### 6.2 重点场景二：新增套餐

当前方法：

```text
SetmealServiceImpl.save
```

它做了：

```text
1. 插入 setmeal
2. 插入 setmeal_dish
```

这也应该是事务。

如果套餐插入成功，但套餐菜品关系插入失败，数据就坏了。

建议：

```text
给 save、update、delete 这些涉及 setmeal + setmeal_dish 的方法补事务。
```

### 6.3 重点场景三：修改菜品

当前方法：

```text
DishServiceImpl.update
```

它做了：

```text
1. 修改 dish
2. 删除原 dish_flavor
3. 插入新 dish_flavor
```

这也应该用事务。

否则可能出现：

```text
菜品更新了，
口味删除了，
新口味没插入成功。
```

### 6.4 你要特别练的事务坑

重点学习这些：

```text
1. RuntimeException 默认回滚，普通 Exception 默认不回滚。
2. try-catch 把异常吞掉，事务可能不回滚。
3. 同一个类内部 this.xxx() 调用，可能导致事务失效。
4. private 方法上加 @Transactional 没意义。
5. 事务范围不能太大，不要把外部接口调用长时间放在事务里。
```

### 6.5 这一阶段的验收标准

完成后你应该能回答：

```text
1. 下单为什么必须加事务？
2. 套餐新增为什么必须加事务？
3. 什么异常会触发事务回滚？
4. 如果插入订单成功后插入明细失败，会发生什么？
5. 如何手动验证事务回滚？
```

## 7. 第三阶段：把订单状态机做扎实

订单是这个项目最值得深挖的业务模块。

因为订单不是 CRUD。

订单是：

```text
状态 + 规则 + 流程 + 异常分支
```

### 7.1 当前订单状态

`Orders` 里已经定义了：

```text
PENDING_PAYMENT = 1       待付款
TO_BE_CONFIRMED = 2       待接单
CONFIRMED = 3             已接单
DELIVERY_IN_PROGRESS = 4  派送中
COMPLETED = 5             已完成
CANCELLED = 6             已取消
```

支付状态：

```text
UN_PAID = 0
PAID = 1
REFUND = 2
```

这是非常好的状态机训练材料。

### 7.2 先画状态流转表

建议你先在文档里写出这张表：

| 当前状态 | 操作 | 新状态 | 谁能操作 | 额外动作 |
| --- | --- | --- | --- | --- |
| 待付款 | 支付成功 | 待接单 | 用户/支付回调 | 设置支付状态为已支付、结账时间 |
| 待付款 | 用户取消 | 已取消 | 用户 | 设置取消原因、取消时间 |
| 待付款 | 超时未支付 | 已取消 | 定时任务 | 设置取消原因、取消时间 |
| 待接单 | 商家接单 | 已接单 | 管理端 | 通知用户 |
| 待接单 | 商家拒单 | 已取消 | 管理端 | 退款、记录拒单原因 |
| 已接单 | 派送 | 派送中 | 管理端 | 可记录派送时间 |
| 派送中 | 完成 | 已完成 | 管理端/定时任务 | 设置送达时间 |
| 待接单/已接单/派送中 | 用户催单 | 状态不变 | 用户 | WebSocket 通知商家 |

写完表，再对照代码改。

### 7.4 重点检查几个真实问题

#### 问题一：支付前要校验订单状态

`payment` 里不应该只根据订单号更新。

应该先查订单：

```text

2. 订单是否属于当前用户？

4. 是否已经支付过？
```

否则可能出现：

```text

别人的订单被支付。

```

#### 问题二：取消订单的更新方式要小心

当前 `updateByNumber` 是固定 SQL：

```sql
update orders
set status = #{status},
    pay_status = #{payStatus},
    checkout_time = #{checkoutTime}
where number = #{number}
```

如果某次只想更新状态，但 `payStatus` 是 null，就可能把数据库里的 `pay_status` 更新成 null。

更稳的做法：

```text
1. 支付成功用专门的 updatePaidByNumber。
2. 普通状态更新用 XML 动态 update。
3. 根据 id 更新比根据 number 更新更明确。
```

这是非常好的 MyBatis 动态 SQL 练习点。

#### 问题三：催单状态要重新确认

注释里写：

```text
只有已接单和派送中可以催单
```

但代码里判断的是：

```java
if (!orders.getStatus().equals(Orders.TO_BE_CONFIRMED)) {
    throw new OrderBusinessException(MessageConstant.ORDER_STATUS_ERROR);
}
```

这和注释不一致。

你可以把它作为练习：

```text
先明确业务规则。
再让代码和规则一致。
```

## 9. 第五阶段：系统化改造 Redis 缓存

你项目里已经用了 Redis。

这很好。

但下一步要从：

```text

```

升级成：


### 9.1 当前 Redis 使用情况

已有场景：

```text

2. 用户端菜品列表：dish_{categoryId}

5. 管理端修改套餐后 @CacheEvict 清理 setmealCache
```

这是非常适合学习缓存的基础。

### 9.2 第一件事：统一缓存 key

建议建立常量：

```java
public class RedisKeyConstant {
    public static final String SHOP_STATUS = "shop:status";
    public static final String DISH_CATEGORY = "dish:category:";
    public static final String SETMEAL_CATEGORY = "setmeal:category:";
}
```

比下面这种更清晰：

```text

setmealCache::1
```

统一 key 的价值：

```text
1. 不容易写错。
2. 一眼知道数据含义。
3. 后面排查 Redis 时更清楚。
```

### 9.3 第二件事：给缓存加过期时间

当前菜品列表缓存：

```java
redisTemplate.opsForValue().set(key, list);
```

建议学习加过期时间：

```java
redisTemplate.opsForValue().set(key, list, 30, TimeUnit.MINUTES);
```

为什么？

```text
即使缓存清理漏了，过期时间也能兜底。
```

### 9.4 第三件事：把缓存逻辑从 Controller 下沉

当前 `DishController` 里有：

```text
查 Redis
查数据库
写 Redis
删除 Redis
```

对于学习来说能理解流程很好。

但进阶后更推荐：

```text
Controller 只处理 HTTP。
Service 处理业务和缓存策略。
```

也就是说，后面可以把缓存逻辑移动到：

```text
DishServiceImpl.list
DishServiceImpl.save/update/delete/startOrStop
```

这样 Controller 更干净。

### 9.5 第四件事：手动缓存和 Spring Cache 二选一或明确边界

现在项目里同时有：

```text
菜品：RedisTemplate 手动缓存
套餐：Spring Cache 注解缓存
```

这正好适合你对比学习。

你可以写一份小总结：

| 方式 | 优点 | 缺点 |
| --- | --- | --- |
| RedisTemplate | 控制细，key、TTL、序列化都能自己管 | 代码多，容易散 |
| Spring Cache | 注解简单，业务代码少 | 复杂 key、复杂失效策略不如手动直观 |

当前阶段建议：

```text
先保留两种方式，理解差异。
后面再考虑统一。
```

### 9.6 第五件事：学习缓存一致性

你要明确一个最常用策略：

```text
查询：
  先查缓存
  缓存没有查数据库
  数据库查到后写缓存

修改：
  先修改数据库
  再删除缓存
```

为什么修改后通常是删除缓存，而不是更新缓存？

```text
删除更简单。
下次查询会重新加载最新数据。
```

## 10. 第六阶段：补 SQL 性能和 N+1 查询问题

## 12. 第八阶段：补库存、限购、防重复提交这些商业场景

外卖项目天然不一定有库存，但你可以加一个轻量库存场景来练并发。

不要一上来做分布式秒杀。

先做单体版。

### 12.1 加库存的最小方案

可以给菜品加：

```text
stock
```

或者单独建：

```text
dish_stock:
  id
  dish_id
  stock
  update_time
```

学习阶段推荐先单独建表，避免大量影响原实体。

### 12.2 下单时扣库存

下单流程升级：

```text
1. 查询购物车。
2. 校验店铺是否营业。
3. 校验菜品/套餐是否还在起售。
4. 扣减库存。
5. 插入订单。
6. 插入订单明细。
7. 清空购物车。
```

库存扣减核心 SQL：

```sql
update dish_stock
set stock = stock - #{count}
where dish_id = #{dishId}
  and stock >= #{count}
```

然后判断影响行数：

```text
影响行数 = 1，扣减成功。
影响行数 = 0，库存不足。
```

你要理解：

```text
不要先 select stock，再 update stock。
高并发下两个请求可能都查到库存足够。
```

### 12.3 防重复提交

新手常见问题：

```text
用户连续点击两次提交订单。
```

简单练习方案：

```text
1. 前端提交时带 requestId。
2. 后端用 Redis SETNX 保存 requestId。
3. 已存在则认为重复提交。
4. 设置短过期时间，比如 5 分钟。
```

这能练：

```text

幂等
接口安全
用户体验
```

### 12.4 限购

可以加一个简单规则：

```text
同一个用户同一个菜品每天最多购买 N 份。
```

实现思路：

```text
1. 查询当天该用户已完成或已支付订单中这个菜品的数量。
2. 加上本次购物车数量。
3. 超过限制则拒绝。
```


### 12.5 这一阶段不要做什么

## 15. 第十一阶段：再考虑消息队列和微服务扩展

等前面 10 个阶段做完，你再考虑 MQ 和微服务会更稳。

### 15.1 先从“订单事件”理解 MQ

未来可以抽象这些事件：

```text
OrderPaidEvent
OrderCancelledEvent
OrderCompletedEvent
StockDeductedEvent
```

事件产生后，可以触发：

```text
发送通知
更新销量
写操作日志
更新报表缓存
发优惠券
```

这时你就能理解 MQ 的价值：

```text
订单主流程不关心所有后续动作。
后续动作可以异步处理。
失败后可以重试。
```

### 15.2 先做本地事件，再上 MQ

你可以先不用 RabbitMQ/Kafka。

先在 Service 里抽象：

```text
订单支付成功后，调用一个 OrderEventService。
```

以后再把它换成 MQ。

这样学得更自然。

### 15.3 微服务拆分预演

等单体清楚后，再思考拆分：

```text
user-service
product-service
order-service
report-service
gateway-service
```

但拆之前必须能回答：

```text
订单服务为什么要调用商品服务？
商品服务不可用时订单怎么办？
库存扣减和订单创建如何保证一致？
报表服务查谁的数据？
用户身份如何在服务间传递？
```

如果回答不出来，先不要拆。

### 15.4 MQ 和微服务不是下一步主线

你的当前主线仍然是：

```text
把单体项目做扎实。
```

等你已经能说清：

```text
事务
状态机
缓存
权限
并发
测试
部署
```

再上 MQ 和微服务，才不会只是搭架子。

## 18. 最后的执行原则

### 18.1 每次只深挖一个主题

不要一边改报表，一边改 Redis，一边改状态机，一边加库存。

这样很容易乱。

建议：

```text
一周一个主题。
一个主题一组提交。
每次改完能运行。
```

### 18.2 先写规则，再写代码

尤其是订单、库存、权限。

先写：

```text
什么状态能做什么？
什么用户能操作什么数据？
什么情况下库存扣减成功？
什么情况下缓存要删除？
```

再写代码。

这就是从“写接口”升级成“做业务”。

### 18.3 不要害怕发现问题

你现在发现：

```text
这个方法没事务。
这个状态判断不严谨。
这个 SQL 查全表。
这个缓存清理不完整。
这个接口可能越权。
```

这不是项目失败。

这是学习价值。

真实后端能力就是在这些细节里长出来的。

### 18.4 这个项目最终可以变成你的代表项目

如果你按这篇路线深挖完，它就不只是：

```text
一个苍穹外卖学习项目。
```

而会变成：

```text
一个包含订单状态机、事务一致性、报表统计、Redis 缓存、权限校验、定时任务、WebSocket 通知、库存扣减、接口测试和部署经验的 Java Web 项目。
```

这就已经很接近企业级 Java 后端入门项目了。

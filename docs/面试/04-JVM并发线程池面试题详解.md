# 04 - JVM、并发、线程池面试题详解

> 复习目标：能讲清 JVM 运行时结构、GC 基础、Java 内存模型、锁、线程池和常见并发问题，并能联系 Web 后端项目。

## 1. JVM 面试的核心

JVM 题通常考三类：

1. 对象在内存里怎么放。
2. 垃圾回收怎么判断对象能不能回收。
3. 线上出现 OOM、CPU 飙高、频繁 GC 时怎么排查。

初级面试不用把每个 GC 算法源码背下来，但必须能把内存区域、GC Roots、常见 OOM 和排查思路讲清楚。

## 2. JVM 运行时内存区域有哪些？

### 答案

常见划分包括：

1. 程序计数器：记录当前线程执行到哪条字节码指令。
2. Java 虚拟机栈：每个方法调用会创建栈帧，保存局部变量表、操作数栈、返回地址等。
3. 本地方法栈：服务 native 方法。
4. 堆：存放大多数对象实例，是 GC 的主要区域。
5. 方法区：存放类元信息、常量、静态变量等；在 HotSpot 中 JDK 8 后主要对应元空间。

### 讲解

线程私有：

1. 程序计数器。
2. 虚拟机栈。
3. 本地方法栈。

线程共享：

1. 堆。
2. 方法区/元空间。

常见异常：

1. 栈太深：`StackOverflowError`。
2. 堆内存不足：`OutOfMemoryError: Java heap space`。
3. 元空间不足：`OutOfMemoryError: Metaspace`。

## 3. 对象什么时候可以被回收？

### 答案

JVM 主流使用可达性分析。它从 GC Roots 出发，如果一个对象无法从任何 GC Roots 通过引用链到达，就说明这个对象不可达，可以被回收。

### 常见 GC Roots

1. 虚拟机栈中局部变量引用的对象。
2. 方法区中静态字段引用的对象。
3. 方法区中常量引用的对象。
4. 本地方法栈中 JNI 引用的对象。
5. 被 synchronized 锁持有的对象。

### 为什么不用引用计数？

引用计数无法很好处理循环引用。例如 A 引用 B，B 引用 A，但外部已经没有任何对象引用它们。引用计数都不为 0，但它们其实应该被回收。

## 4. 强引用、软引用、弱引用、虚引用有什么区别？

### 答案

| 引用类型 | 回收时机 | 常见用途 |
| --- | --- | --- |
| 强引用 | 只要可达就不回收 | 普通对象引用 |
| 软引用 | 内存不足时可能回收 | 缓存，但现在业务缓存更常用 Redis/Caffeine |
| 弱引用 | 下次 GC 时回收 | ThreadLocalMap 的 key |
| 虚引用 | 不决定对象生命周期 | 跟踪对象回收、堆外内存清理 |

### ThreadLocal 追问

ThreadLocalMap 的 key 是弱引用，但 value 不是弱引用。如果线程长期存活，并且没有 remove，value 可能残留在线程里，导致内存泄漏。因此 Web 项目中使用 ThreadLocal 保存用户 id，请求结束后要清理。

## 5. 常见垃圾回收算法有哪些？

### 答案

1. 标记-清除：标记可回收对象，再清除；缺点是内存碎片。
2. 标记-复制：把存活对象复制到另一块区域；适合新生代，因为对象朝生夕死。
3. 标记-整理：标记后把存活对象向一端移动；适合老年代，减少碎片。
4. 分代收集：根据对象生命周期不同，把堆分为新生代、老年代，采用不同策略。

### 面试讲法

新生代对象大多数很快死亡，所以适合复制算法；老年代对象存活率高，如果复制成本太大，更适合标记-清除或标记-整理。

## 6. 类加载过程是什么？

### 答案

类加载大致包括：加载、验证、准备、解析、初始化。

1. 加载：读取 class 字节码，生成 Class 对象。
2. 验证：确保字节码符合 JVM 规范。
3. 准备：为静态变量分配内存并设置默认值。
4. 解析：把符号引用替换为直接引用。
5. 初始化：执行静态变量赋值和静态代码块。

### 常见追问

静态变量什么时候赋值？

准备阶段先赋默认值，初始化阶段才执行代码里的显式赋值。

```java
public static int count = 10;
```

准备阶段 `count = 0`，初始化阶段 `count = 10`。

## 7. 双亲委派机制是什么？

### 答案

类加载器收到加载请求时，先委托父加载器加载；父加载器加载不了，子加载器才尝试加载。这样可以避免核心类被重复加载或被恶意替换。

### 讲解

比如你自己写一个 `java.lang.String`，正常情况下不会替换 JDK 的 String 类，因为启动类加载器会优先加载 JDK 自带的核心类。

### 扩展

有些框架会打破双亲委派，比如 Tomcat 为了隔离不同 Web 应用的类，SPI 为了让核心类加载器加载到第三方实现。

## 8. Java 内存模型 JMM 解决什么问题？

### 答案

JMM 规定了多线程下变量如何在主内存和工作内存之间交互，解决可见性、原子性和有序性问题。

三类问题：

1. 可见性：一个线程修改变量，其他线程是否马上看见。
2. 原子性：一个操作是否不可分割。
3. 有序性：代码执行顺序是否可能被重排序。

## 9. volatile 有什么作用？

### 答案

`volatile` 保证可见性和一定程度的有序性，但不保证复合操作的原子性。

### 讲解

适合场景：

```java
private volatile boolean running = true;
```

一个线程修改 `running = false`，另一个线程能及时看到。

不适合场景：

```java
volatile int count = 0;
count++;
```

`count++` 包括读取、加一、写回三个步骤，不是原子操作。多线程下仍然可能丢失更新。

### 面试扩展

单例双重检查锁为什么要 volatile？

因为对象创建不是一步完成，可能发生指令重排序。`volatile` 可以禁止相关重排序，避免其他线程看到“引用不为 null 但对象还没初始化完成”的状态。

## 10. synchronized 和 ReentrantLock 有什么区别？

### 答案

`synchronized` 是 JVM 层面的关键字，使用简单，自动加锁和释放锁；`ReentrantLock` 是 JUC 提供的显式锁，需要手动 lock/unlock，但功能更丰富，比如可中断锁、公平锁、尝试获取锁、多个条件队列。

### 对比

| 点 | synchronized | ReentrantLock |
| --- | --- | --- |
| 使用方式 | 关键字 | API |
| 释放锁 | 自动释放 | 必须 finally unlock |
| 公平锁 | 不支持指定 | 支持 |
| 可中断 | 不灵活 | 支持 lockInterruptibly |
| 条件队列 | 一个 wait/notify 队列 | 多个 Condition |

### 推荐表达

普通同步优先用 `synchronized`，代码简单不容易忘记释放。需要更复杂锁能力时再用 `ReentrantLock`。

## 11. CAS 是什么？有什么问题？

### 答案

CAS 是 Compare And Swap，比较并交换。它会比较内存中的值是否等于预期值，如果相等就更新为新值，否则失败重试。CAS 是很多无锁并发类的基础，比如 AtomicInteger。

### 问题

1. ABA 问题：值从 A 变 B 又变 A，CAS 认为没变。
2. 自旋开销：竞争激烈时一直重试，浪费 CPU。
3. 只能保证单个变量的原子更新，复杂一致性仍要加锁或使用事务。

### ABA 解决

使用版本号或时间戳，例如 `AtomicStampedReference`。

## 12. 线程池为什么重要？

### 答案

线程创建和销毁有成本。如果每个请求或任务都新建线程，会导致资源浪费，甚至把机器打爆。线程池通过复用线程、控制并发数量、管理任务队列，提高系统稳定性。

### 项目联系

后端项目中，异步发送通知、导出报表、调用第三方接口、批量处理任务，都可能用线程池。但涉及事务、用户上下文、异常处理时要特别谨慎。

## 13. ThreadPoolExecutor 核心参数有哪些？

### 答案

1. `corePoolSize`：核心线程数。
2. `maximumPoolSize`：最大线程数。
3. `keepAliveTime`：非核心线程空闲存活时间。
4. `workQueue`：任务队列。
5. `threadFactory`：线程工厂，可设置线程名。
6. `handler`：拒绝策略。

### 执行流程

1. 当前线程数小于核心线程数：创建核心线程执行任务。
2. 核心线程满了：任务进入队列。
3. 队列满了，当前线程数小于最大线程数：创建非核心线程。
4. 线程数达到最大且队列满：触发拒绝策略。

### 常见队列

| 队列 | 特点 |
| --- | --- |
| ArrayBlockingQueue | 有界数组队列 |
| LinkedBlockingQueue | 链表队列，可有界也可无界 |
| SynchronousQueue | 不存储任务，直接移交 |
| PriorityBlockingQueue | 优先级队列 |

### 不推荐 Executors 的原因

`Executors.newFixedThreadPool` 默认使用无界队列，任务堆积可能导致 OOM；`newCachedThreadPool` 最大线程数过大，可能创建过多线程。生产环境建议显式创建 `ThreadPoolExecutor`。

## 14. 拒绝策略有哪些？

### 答案

1. AbortPolicy：直接抛异常，默认策略。
2. CallerRunsPolicy：由提交任务的线程自己执行。
3. DiscardPolicy：直接丢弃任务，不抛异常。
4. DiscardOldestPolicy：丢弃队列最老任务，再提交新任务。

### 怎么选

业务不能丢时，不要静默丢弃。可以使用 AbortPolicy 让问题暴露，或 CallerRunsPolicy 做削峰，但要评估调用线程被阻塞的影响。关键任务还可以落库或发 MQ，失败后重试。

## 15. 线程池参数怎么设置？

### 答案

没有万能公式，要看任务类型、机器配置、响应时间要求和下游承载能力。

一般思路：

1. CPU 密集型：线程数接近 CPU 核数，避免频繁上下文切换。
2. IO 密集型：线程数可以大于 CPU 核数，因为线程经常等待 IO。
3. 下游有限制：线程数不能超过数据库连接池、Redis、第三方接口承载能力。
4. 队列必须有界，避免无限堆积。
5. 线程名要清晰，方便排查。

### 面试表达

```text
我不会只按公式设置。
我会先判断任务是 CPU 密集还是 IO 密集，再结合机器核数、接口耗时、QPS、数据库连接池和压测结果调整。
同时队列要有界，拒绝策略要能暴露问题或做降级。
```

## 16. ThreadLocal 是什么？

### 答案

ThreadLocal 为每个线程提供一份独立变量副本。不同线程访问同一个 ThreadLocal，拿到的是自己线程内部保存的值。

### 项目联系

当前项目用 BaseContext 保存当前用户 id。拦截器解析 JWT 后把用户 id 放进 ThreadLocal，Service 层就能获取当前登录用户。

### 风险

Web 容器线程池会复用线程。如果请求结束后不 remove，下一次请求可能拿到上一次用户 id，或者导致 value 长期无法释放。因此建议在拦截器 `afterCompletion` 或 finally 中清理。

## 17. 什么是死锁？怎么排查？

### 答案

死锁是多个线程互相等待对方持有的资源，导致都无法继续执行。

四个必要条件：

1. 互斥。
2. 占有且等待。
3. 不可抢占。
4. 循环等待。

### 避免方式

1. 固定加锁顺序。
2. 减少锁范围。
3. 使用 tryLock 设置超时。
4. 避免锁内调用外部接口或耗时操作。

### 排查方式

1. 使用 `jstack` 查看线程堆栈。
2. 查找 BLOCKED、WAITING 线程。
3. 分析线程持有哪些锁、等待哪些锁。
4. 根据堆栈定位代码。

## 18. CompletableFuture 有什么用？

### 答案

`CompletableFuture` 用于异步编排，可以把多个异步任务串行、并行、组合执行。适合多个互不依赖的远程调用或查询并行执行，降低总耗时。

### 示例

```java
CompletableFuture<User> userFuture =
    CompletableFuture.supplyAsync(() -> queryUser(userId), executor);

CompletableFuture<List<Order>> orderFuture =
    CompletableFuture.supplyAsync(() -> queryOrders(userId), executor);

CompletableFuture.allOf(userFuture, orderFuture).join();
```

### 注意

1. 一定要指定自定义线程池。
2. 要处理异常。
3. 不要把数据库打爆。
4. 注意事务和 ThreadLocal 上下文不会自动传播。

## 19. 虚拟线程要不要准备？

### 答案

虚拟线程是现代 Java 的重要特性，JDK 21 已正式引入。它适合大量阻塞 IO 任务，可以显著降低线程资源成本。但很多企业项目仍在 Java 8、11、17 或 21，是否使用要看公司 JDK 版本和框架兼容性。

### 面试表达

```text
我了解虚拟线程主要是为了解决传统平台线程成本高的问题，适合大量阻塞 IO 场景。
但在当前 Spring Boot 2.7 的项目里，我不会直接引入虚拟线程，因为还要考虑 JDK 版本、框架兼容和监控排查。
如果公司已经使用较新 JDK 和 Spring Boot 3.x，可以进一步评估。
```

## 20. 线上 CPU 飙高怎么排查？

### 答案

排查顺序：

1. `top` 找到 CPU 高的 Java 进程。
2. `top -Hp <pid>` 找到 CPU 高的线程。
3. 把线程 id 转成 16 进制。
4. `jstack <pid>` 找到对应线程堆栈。
5. 看是否死循环、频繁 GC、锁竞争、正则回溯、JSON 序列化等。

面试中可以讲思路，不一定要现场背命令所有细节。

## 21. 线上 OOM 怎么排查？

### 答案

1. 先看 OOM 类型：堆、元空间、直接内存、线程过多。
2. 保存 heap dump。
3. 用 MAT、VisualVM、JProfiler 等工具分析大对象和引用链。
4. 看是否集合无限增长、缓存无过期、ThreadLocal 未清理、查询一次加载太多数据。
5. 修复后压测和监控验证。

### 项目联系

如果订单导出一次查出大量数据再写 Excel，可能导致内存飙升。更稳的做法是分页查询、流式写出、限制导出范围。

# 08 - 分布式、微服务、消息队列场景题详解

> 复习目标：不是硬背微服务名词，而是能用“业务问题 -> 技术方案 -> 风险 -> 兜底”的方式回答场景题。

## 1. 初级候选人怎么准备分布式题？

如果你没有真实微服务生产经验，不要在简历上写“精通微服务架构”。但你应该理解常见问题：

1. 服务之间怎么通信。
2. 接口失败怎么重试。
3. 重复请求怎么幂等。
4. 消息如何保证可靠。
5. 缓存和数据库如何一致。
6. 分布式锁解决什么问题。
7. 限流、熔断、降级解决什么问题。

面试中可以明确说：

```text
我当前项目是单体 Spring Boot 项目，但我理解这些分布式问题在订单、支付、通知、库存这些场景里会出现。
如果把项目升级为微服务，我会优先拆用户、商品、订单、支付、通知这些边界，同时重点处理接口幂等、事务一致性和消息可靠性。
```

## 2. 什么是微服务？

### 答案

微服务是把一个大系统按业务边界拆成多个小服务，每个服务独立开发、部署、扩展，通过 HTTP/RPC/MQ 等方式通信。

### 优点

1. 服务边界清晰。
2. 可以独立部署和扩容。
3. 不同团队可并行开发。
4. 单个服务故障影响范围可控。

### 缺点

1. 系统复杂度上升。
2. 分布式事务变复杂。
3. 调用链路变长，排查困难。
4. 网络调用失败不可避免。
5. 需要注册中心、配置中心、网关、链路追踪、监控等基础设施。

### 面试注意

不要为了显得高级而把小项目强行拆微服务。单体项目业务还没复杂到一定程度时，清晰单体比混乱微服务更好。

## 3. 如果把苍穹外卖拆成微服务，怎么拆？

### 答案

可以按业务边界拆：

1. 用户服务：用户登录、地址簿。
2. 员工/权限服务：员工登录、权限。
3. 商品服务：分类、菜品、套餐。
4. 订单服务：购物车、下单、订单状态。
5. 支付服务：支付单、支付回调、退款。
6. 通知服务：WebSocket、短信、站内信。
7. 报表服务：营业额、销量、用户统计。

### 讲解

拆服务不是按 Controller 文件夹拆，而是按业务能力和数据归属拆。订单服务不应该直接改商品服务数据库，服务之间应通过接口或消息协作。

### 风险

1. 下单要调用商品、库存、优惠、支付等服务，链路变长。
2. 任何远程调用都可能失败。
3. 原本一个本地事务能解决的问题变成分布式一致性问题。
4. 日志、监控、链路追踪必须补齐。

## 4. CAP 和 BASE 怎么理解？

### CAP

分布式系统中：

1. Consistency 一致性。
2. Availability 可用性。
3. Partition tolerance 分区容错性。

网络分区不可避免时，系统通常要在一致性和可用性之间取舍。

### BASE

BASE 是一种最终一致性思想：

1. Basically Available：基本可用。
2. Soft state：软状态。
3. Eventually consistent：最终一致。

### 面试表达

订单支付这种核心链路更重视一致性；消息通知、报表统计可以接受最终一致。

## 5. 为什么使用消息队列？

### 答案

MQ 常见作用：

1. 异步：把非核心耗时操作异步处理。
2. 削峰：高峰请求先进入队列，消费者按能力处理。
3. 解耦：生产者不需要直接依赖消费者。
4. 广播：一个事件可被多个消费者处理。
5. 最终一致：通过消息驱动多个系统最终同步。

### 项目例子

支付成功后：

```text
订单服务更新订单状态 -> 发送 OrderPaid 事件
通知服务消费事件 -> WebSocket 通知商家
积分服务消费事件 -> 增加积分
报表服务消费事件 -> 更新统计
```

这样订单服务不需要同步调用所有后续服务。

## 6. MQ 如何保证消息不丢？

### 答案

要看三个环节：

1. 生产者到 Broker。
2. Broker 自身存储。
3. Broker 到消费者。

### 生产者

1. 发送确认机制。
2. 失败重试。
3. 本地消息表，先落库再发送。

### Broker

1. 消息持久化。
2. 主从复制或集群。
3. 合理 ack 配置。

### 消费者

1. 手动 ack。
2. 业务处理成功后再 ack。
3. 失败重试和死信队列。

### 面试表达

```text
我不会只说 MQ 保证消息不丢。
可靠性要分生产者、Broker、消费者三个阶段看。
生产者要确认发送成功，Broker 要持久化，消费者要处理成功后再 ack。
同时还要设计幂等，因为可靠重试通常会带来重复消息。
```

## 7. MQ 消息重复怎么办？

### 答案

消息重复是正常情况。解决方式是消费端幂等。

常见幂等方案：

1. 业务唯一键，比如订单号、支付流水号。
2. 数据库唯一索引。
3. Redis `SETNX` 防重复。
4. 消费记录表。
5. 状态机判断。

### 项目例子

支付成功消息可能重复投递。消费端更新订单状态时可以判断：

```text
如果订单已支付，直接返回成功，不重复处理。
如果订单未支付，才更新为已支付。
```

如果是增加积分，必须用支付流水号建唯一消费记录，避免重复加积分。

## 8. MQ 消息顺序怎么保证？

### 答案

如果业务要求同一个订单的消息按顺序处理，可以让同一个订单号的消息进入同一个队列或同一个分区，由单个消费者顺序消费。

### 注意

全局有序成本很高，吞吐量低。大多数业务只需要局部有序，比如同一个订单有序，而不是所有订单全局有序。

## 9. MQ 消息积压怎么办？

### 答案

排查：

1. 消费者是否异常。
2. 下游数据库或接口是否慢。
3. 消费线程数是否太少。
4. 单条消息处理是否太重。
5. 是否出现大量重试。

处理：

1. 临时扩容消费者。
2. 优化慢 SQL 或下游接口。
3. 批量消费。
4. 拆分 Topic/队列。
5. 对失败消息进入死信队列，避免阻塞正常消息。

## 10. 什么是死信队列？

### 答案

死信队列用于存放无法正常消费的消息，比如多次重试仍失败、消息过期、队列满等。它可以避免坏消息一直阻塞主队列。

### 使用方式

1. 主队列消费失败后重试。
2. 超过最大次数进入死信队列。
3. 运维或后台任务分析死信原因。
4. 修复后人工或自动补偿。

## 11. 分布式事务怎么解决？

### 答案

常见方案：

1. 2PC/XA：强一致，但性能和可用性较差。
2. TCC：Try、Confirm、Cancel，业务侵入强。
3. Saga：长事务拆成多个本地事务和补偿动作。
4. 本地消息表：本地事务写业务数据和消息表，再异步投递消息。
5. MQ 事务消息：用消息中间件提供的事务消息能力。
6. 最大努力通知：适合支付回调等通知场景。

### 面试建议

初级面试重点讲本地消息表和最终一致即可。

### 本地消息表示例

```text
订单服务本地事务：
1. 更新订单状态为已支付
2. 插入一条待发送消息 OrderPaid

后台任务扫描消息表：
1. 发送 MQ
2. 成功后把消息状态改为已发送
3. 失败则重试
```

优点是业务数据和消息记录在同一个数据库事务里，不会出现订单改了但消息完全没记录的问题。

## 12. 接口幂等是什么？

### 答案

接口幂等是指同一个请求执行一次和执行多次，最终结果一致。它用于解决重复点击、网络重试、MQ 重复消费、支付重复回调等问题。

### 常见方案

1. Token 防重复提交。
2. 业务唯一索引。
3. 状态机判断。
4. Redis `SETNX`。
5. 请求流水号。

### 项目例子

下单防重复：

```text
前端进入提交页时获取 submitToken。
用户提交订单时带上 token。
后端用 Redis SETNX 校验 token，只允许第一次成功。
订单创建成功后 token 失效。
```

支付回调幂等：

```text
根据支付流水号或订单号查询状态。
如果已支付，直接返回成功。
如果未支付，才更新订单状态。
```

## 13. 限流、熔断、降级有什么区别？

### 限流

限制请求流量，避免系统被打垮。

例子：

1. 每个用户每秒最多提交 1 次订单。
2. 登录接口按 IP 限流。

### 熔断

当下游服务持续失败时，暂时停止调用，快速失败，避免拖垮自己。

### 降级

核心功能保留，非核心功能关闭或返回简化结果。

例子：

1. 报表统计暂时返回缓存。
2. 推荐列表失败时返回默认列表。

## 14. 分布式锁适合什么场景？

### 答案

分布式锁适合多个服务实例同时竞争同一份资源的场景，比如：

1. 防止同一订单重复处理。
2. 定时任务多实例只执行一次。
3. 秒杀库存扣减。
4. 缓存重建互斥。

### 注意

分布式锁不是万能的。关键业务还要配合唯一索引、状态机和幂等。

## 15. 高并发下单怎么设计？

### 答案思路

先说明不是所有外卖下单都需要秒杀级架构。普通下单重点是事务、库存、幂等和数据库承载。

如果是高并发库存场景，可以这样设计：

1. 前端防重复提交。
2. 网关限流。
3. Redis 预扣库存。
4. 请求写入 MQ 削峰。
5. 消费者异步创建订单。
6. 数据库唯一约束防重复。
7. 失败补偿库存。
8. 用户端查询订单创建结果。

### 风险

1. Redis 扣了库存但订单创建失败，需要补偿。
2. MQ 积压导致用户等待。
3. 重复消费要幂等。
4. 数据库库存仍要最终校验，Redis 不能作为唯一事实来源。

## 16. WebSocket 多实例怎么处理？

### 问题

单机时，WebSocket session 保存在本机内存里。多实例部署后，用户连接可能在 A 机器，但业务消息在 B 机器产生，B 机器找不到 session。

### 方案

1. 网关层做粘性会话，让同一用户尽量连同一实例。
2. 使用 Redis Pub/Sub 或 MQ 广播消息，各实例收到后只给本机在线用户发送。
3. 使用专门 WebSocket 网关统一管理连接。
4. 在线状态存 Redis，记录用户在哪个节点。

### 面试表达

当前项目单机 HashMap 保存 session 适合学习。生产多实例要改 ConcurrentHashMap，并引入跨节点消息转发。

## 17. 第三方接口失败怎么处理？

### 答案

比如调用微信支付、文件存储、短信服务失败：

1. 设置合理超时，不要无限等待。
2. 对可重试错误进行有限次数重试。
3. 重试要幂等。
4. 失败记录日志和告警。
5. 核心链路可异步化。
6. 提供补偿任务。

### 项目例子

支付回调处理失败时，第三方通常会重试通知。服务端必须保证回调幂等，并能通过订单号或支付流水号重复处理。

## 18. 场景题回答模板

遇到场景题，按这个顺序回答：

1. 明确业务目标：要解决什么问题。
2. 估算约束：QPS、数据量、一致性要求、是否允许延迟。
3. 先给简单可靠方案。
4. 再按瓶颈升级：缓存、MQ、分库分表、异步、限流。
5. 说风险：幂等、一致性、消息丢失、重复消费。
6. 说兜底：重试、补偿、监控、告警、人工处理。

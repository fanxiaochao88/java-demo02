# 07 - Redis 缓存、分布式锁面试题详解

> 复习目标：能回答 Redis 数据结构、缓存模式、缓存一致性、穿透/击穿/雪崩、分布式锁、持久化和项目落地。

## 1. Redis 在 Java 后端里解决什么问题？

Redis 常见用途：

1. 缓存热点数据，减轻 MySQL 压力。
2. 保存临时数据，比如验证码、登录态、限流计数。
3. 做分布式锁。
4. 做排行榜、计数器、签到等数据结构场景。
5. 做消息通知或简单队列，但复杂可靠消息更推荐 MQ。

面试里不要说“Redis 就是内存数据库”就结束，要说它在项目里解决了什么问题。

## 2. Redis 为什么快？

### 答案

Redis 快主要因为：

1. 数据主要在内存中。
2. 使用高效的数据结构。
3. 单线程执行命令，避免多线程锁竞争。
4. IO 多路复用处理大量连接。
5. C 语言实现，整体开销小。

### 补充

Redis 单线程主要指命令执行核心线程，并不是整个 Redis 进程只有一个线程。新版本中网络 IO、持久化等也有后台线程参与。

## 3. Redis 常见数据类型有哪些？

### 答案

| 类型 | 常见用途 |
| --- | --- |
| String | 缓存对象 JSON、计数器、分布式锁 |
| Hash | 保存对象字段，如用户信息 |
| List | 简单队列、消息列表 |
| Set | 去重集合、共同关注 |
| ZSet | 排行榜、延迟任务 |
| Bitmap | 签到、活跃统计 |
| HyperLogLog | UV 估算 |
| Stream | 消息流 |
| GEO | 地理位置 |

### 项目联系

当前外卖项目可用：

1. String 保存店铺营业状态。
2. String/Hash 缓存菜品或套餐列表。
3. String 保存短信/微信登录验证码。
4. ZSet 做销量排行榜扩展。

## 4. 缓存常见模式是什么？

### 答案

最常见是 Cache Aside Pattern，也叫旁路缓存：

读：

```text
先查 Redis -> 命中直接返回 -> 未命中查 MySQL -> 写入 Redis -> 返回
```

写：

```text
先更新 MySQL -> 再删除 Redis
```

### 为什么通常是删除缓存而不是更新缓存？

因为更新缓存容易出现并发覆盖和复杂组装问题。删除缓存让下一次查询重新从数据库加载，逻辑更简单。

### 项目联系

菜品、套餐、分类列表适合这种模式。订单状态、支付状态这类强一致数据不建议随意缓存。

## 5. 先更新数据库还是先删除缓存？

### 推荐答案

常见策略是：先更新数据库，再删除缓存。

### 为什么不先删缓存？

如果先删缓存，再更新数据库，在并发情况下可能出现：

```text
线程 A 删除缓存
线程 B 查询缓存未命中，查数据库旧值，写回缓存
线程 A 更新数据库为新值
```

结果缓存里又变成旧值。

### 先更新数据库再删除缓存也有问题吗？

有。如果数据库更新成功，删除缓存失败，缓存仍是旧值。

解决方式：

1. 设置合理 TTL，让旧缓存最终过期。
2. 删除失败重试。
3. 使用 MQ 异步重试删除。
4. 订阅 binlog 同步删除缓存。
5. 对一致性要求极高的场景不要使用普通缓存模式。

## 6. 缓存穿透是什么？怎么解决？

### 答案

缓存穿透是查询一个缓存和数据库都不存在的数据，导致每次请求都打到数据库。

解决方式：

1. 参数校验，过滤非法 id。
2. 缓存空值，给短 TTL。
3. 布隆过滤器，提前判断数据是否可能存在。
4. 接口限流和风控。

### 项目例子

用户恶意请求不存在的菜品 id：

```text
/user/dish/999999999
```

如果 Redis 没有、MySQL 也没有，每次都查库。可以把空结果缓存 1-5 分钟，或者使用布隆过滤器拦截明显不存在 id。

## 7. 缓存击穿是什么？怎么解决？

### 答案

缓存击穿是某个热点 key 过期瞬间，大量请求同时打到数据库。

解决方式：

1. 热点 key 不过期或逻辑过期。
2. 互斥锁，只允许一个线程回源重建缓存。
3. 提前刷新缓存。
4. 限流降级。

### 互斥锁思路

```text
查缓存未命中 -> 尝试获取锁
获取成功 -> 查数据库 -> 写缓存 -> 释放锁
获取失败 -> 短暂 sleep 后重试查缓存
```

### 项目例子

店铺营业状态、热门套餐列表可能是热点 key。高峰期如果同时过期，就可能击穿数据库。

## 8. 缓存雪崩是什么？怎么解决？

### 答案

缓存雪崩是大量 key 同时过期，或者 Redis 整体不可用，导致大量请求打到数据库。

解决方式：

1. TTL 加随机值，避免同一时间过期。
2. 热点数据预热。
3. Redis 高可用，主从、哨兵、集群。
4. 本地缓存兜底。
5. 限流、熔断、降级。
6. 数据库保护，避免被打垮。

## 9. Redis 过期删除策略是什么？

### 答案

Redis 不是每个 key 到期就立刻删除。它结合惰性删除和定期删除。

1. 惰性删除：访问 key 时发现过期，再删除。
2. 定期删除：后台定期抽样检查过期 key 并删除。

如果过期 key 没被及时删除且内存不足，就会触发内存淘汰策略。

## 10. Redis 内存淘汰策略有哪些？

### 答案

常见策略：

1. noeviction：不淘汰，写入报错。
2. allkeys-lru：所有 key 中淘汰最近最少使用。
3. volatile-lru：设置过期时间的 key 中淘汰最近最少使用。
4. allkeys-random：所有 key 随机淘汰。
5. volatile-random：设置过期时间的 key 随机淘汰。
6. volatile-ttl：优先淘汰快过期的 key。
7. allkeys-lfu / volatile-lfu：按使用频率淘汰。

### 面试表达

缓存场景常见选择 allkeys-lru 或 allkeys-lfu，但要结合业务。不能被淘汰的重要数据不要只放 Redis。

## 11. Redis 持久化 RDB 和 AOF 有什么区别？

### 答案

RDB 是快照持久化，在某个时间点把内存数据保存成快照文件。AOF 是追加日志，把写命令追加到日志中，重启时重放命令恢复数据。

| 点 | RDB | AOF |
| --- | --- | --- |
| 恢复速度 | 快 | 相对慢 |
| 数据完整性 | 可能丢最近一段数据 | 通常更好 |
| 文件大小 | 较小 | 较大 |
| 适合 | 备份、快速恢复 | 更高数据安全 |

### 面试注意

Redis 即使开启持久化，也不能替代 MySQL。缓存数据要允许丢失或可从数据库重建。

## 12. Redis 分布式锁怎么实现？

### 答案

基础实现使用 `SET key value NX EX seconds`：

```text
SET lock:order:123 requestId NX EX 10
```

含义：

1. NX：key 不存在才设置，保证互斥。
2. EX：设置过期时间，避免死锁。
3. value：保存唯一 requestId，释放锁时校验是不是自己的锁。

### 释放锁为什么要 Lua 脚本？

释放锁需要“判断 value 是否相等”和“删除 key”两个操作原子执行。否则可能误删别人的锁。

Lua 逻辑：

```lua
if redis.call("get", KEYS[1]) == ARGV[1] then
    return redis.call("del", KEYS[1])
else
    return 0
end
```

## 13. 分布式锁有哪些风险？

### 答案

1. 锁过期太短，业务没执行完锁就释放。
2. 锁过期太长，失败后恢复慢。
3. 释放锁没校验 value，误删别人的锁。
4. Redis 主从切换时锁可能丢失。
5. 业务没有幂等，锁失效后仍可能重复执行。

### Redisson

Redisson 提供更完整的分布式锁实现，包括可重入锁、自动续期 watchdog、公平锁等。但使用 Redisson 也不能替代业务幂等。

## 14. RedisTemplate 和 StringRedisTemplate 有什么区别？

### 答案

`StringRedisTemplate` 的 key 和 value 默认都是字符串序列化，适合操作字符串。`RedisTemplate` 更通用，可以配置不同序列化器，存储对象、Hash 等。

### 项目注意

默认 RedisTemplate 可能使用 JDK 序列化，Redis 中数据不易读且跨语言不友好。实际项目常把 key 配成 String 序列化，value 配成 JSON 序列化。

## 15. Spring Cache 和 RedisTemplate 有什么区别？

### 答案

`RedisTemplate` 是手动操作 Redis，控制细；`Spring Cache` 是注解式缓存，开发简单。

| 点 | RedisTemplate | Spring Cache |
| --- | --- | --- |
| 控制粒度 | 高 | 中等 |
| 代码侵入 | 需要手写缓存逻辑 | 注解较少 |
| 适合 | 复杂缓存逻辑 | 标准查询缓存 |
| 风险 | 代码分散 | key 和失效策略要设计好 |

### 项目联系

菜品、套餐缓存可以对比两种方式。简单查询可以用 `@Cacheable`，复杂缓存一致性和批量删除用 RedisTemplate 更直接。

## 16. BigKey 和 HotKey 是什么？

### BigKey

BigKey 是 value 特别大的 key，比如一个 String 几 MB，一个 List/Hash 有几十万元素。

风险：

1. 网络传输慢。
2. 删除阻塞。
3. 内存不均。
4. 主从同步压力。

优化：

1. 拆分 key。
2. 控制单个 value 大小。
3. 使用异步删除。

### HotKey

HotKey 是访问特别频繁的 key。

风险：

1. 单个 Redis 节点压力过大。
2. key 过期瞬间击穿数据库。

优化：

1. 本地缓存。
2. 热点 key 不过期或逻辑过期。
3. 多副本 key。
4. 限流。

## 17. Redis 和 MySQL 数据不一致怎么办？

### 答案

先判断业务能接受什么级别的一致性。

如果是菜品列表这类读多写少数据，短暂不一致可以接受：

1. 先更新数据库，再删除缓存。
2. 设置 TTL。
3. 删除失败重试。

如果是订单支付状态这类强一致数据：

1. 以数据库为准。
2. 避免把状态长期缓存。
3. 必要时查询缓存后再校验数据库。
4. 使用事务、幂等和可靠消息保证状态流转。

## 18. 当前项目 Redis 可以怎么优化？

建议：

1. 统一 Redis key 常量，比如 `shop:status`、`dish:list:{categoryId}`。
2. 给缓存设置 TTL，并添加随机时间。
3. 更新菜品/套餐/分类后删除相关缓存。
4. 缓存空值防穿透。
5. 热点数据启动预热。
6. RedisTemplate 配置泛型和 JSON 序列化。
7. Redis 异常时降级查数据库，避免接口直接崩。

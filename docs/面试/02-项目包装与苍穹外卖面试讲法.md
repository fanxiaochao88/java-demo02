# 02 - 项目包装与苍穹外卖面试讲法

> 目标：把当前 `sky-take-out` 项目从“学习项目”讲成“结构清楚、链路完整、能体现后端能力的项目”。  
> 注意：不要把没有真实做过的生产经验说成已经上线。可以把它们表达为“我整理过的优化方案”和“如果上生产要补的能力”。

## 1. 项目一句话介绍

可以这样说：

```text
这是一个基于 Spring Boot + MyBatis 的外卖业务系统，包含管理端和用户端两类接口。
管理端主要负责员工、分类、菜品、套餐、订单和经营报表；
用户端主要负责微信登录、地址簿、购物车、下单、支付、催单和订单查询。
我重点梳理了登录鉴权、订单状态流转、Redis 缓存、AOP 自动填充、WebSocket 来单提醒和报表统计这些后端链路。
```

如果面试官问“是不是课程项目”，不要慌，可以说：

```text
它的基础来自一个外卖业务练习项目，但我没有只停留在 CRUD。
我重点把请求链路、数据库关系、订单状态、缓存一致性、权限校验和可优化点整理了一遍。
所以我更关注的是通过这个项目训练真实后端开发里会遇到的问题。
```


## 4. 项目主链路讲法

### 4.1 登录鉴权链路

回答模板：

```text
登录成功后，服务端根据用户 id、用户名等信息生成 JWT，返回给前端。
前端后续请求把 token 放到请求头里。
后端拦截器先从请求头取 token，然后校验签名和过期时间，解析出用户 id。
解析成功后，把用户 id 放到 ThreadLocal，也就是项目里的 BaseContext。
这样 Service 层不需要每个方法都传 userId，可以直接从上下文获取当前登录用户。
请求结束后，生产项目里一般要清理 ThreadLocal，避免线程复用导致脏数据。
```

可追问点：

1. JWT 为什么不能存敏感信息？
2. JWT 怎么失效？
3. 拦截器和过滤器有什么区别？
4. ThreadLocal 为什么可能内存泄漏？

### 4.2 下单链路

回答模板：

```text
用户下单时，后端先校验收货地址是否存在，再根据当前用户 id 查询购物车。
如果购物车为空，直接抛业务异常。
如果购物车有商品，就创建订单主表记录，初始化订单状态为待支付，支付状态为未支付，同时生成订单号、下单时间、用户 id、地址和金额。
订单主表插入后拿到主键 id，再把购物车里的每个商品转换成订单明细，批量插入订单明细表。
最后清空购物车，并返回订单 id、订单号、金额和下单时间。
这个链路在生产环境需要加事务，因为订单主表、订单明细和购物车清空要么一起成功，要么一起失败。
```

可追问点：

1. 为什么订单主表和订单明细表分开？
2. 为什么要事务？
3. 订单号为什么不能只用时间戳？
4. 如何防止重复下单？
5. 如何处理库存扣减？

### 4.3 支付和新订单提醒链路

回答模板：

```text
当前项目里支付是模拟成功：根据订单号把订单状态从待支付改为待接单，支付状态改为已支付，并记录支付时间。
随后构造一条新订单提醒消息，通过 WebSocket 推送给管理端。
真实生产环境中，支付不能以前端返回为准，而应该以微信/支付宝的服务端回调为准。
回调里要校验签名、校验金额、校验订单状态，并且要做幂等，避免重复回调导致重复改状态。
```

可追问点：

1. 支付回调为什么要幂等？
2. 支付成功后通知商家失败怎么办？
3. WebSocket 断线怎么处理？
4. 如果有多台后端服务器，WebSocket 会话怎么管理？

### 4.4 Redis 缓存链路

回答模板：

```text
项目里适合缓存读多写少的数据，比如菜品分类、套餐列表、店铺营业状态。
查询时先查 Redis，命中就直接返回；未命中再查 MySQL，然后把结果写入 Redis。
更新菜品或套餐后，需要删除相关缓存，避免用户看到旧数据。
我会优先采用“先更新数据库，再删除缓存”的策略；如果对一致性要求更高，可以引入延迟双删、消息队列重试或者 Canal 订阅 binlog。
```

可追问点：

1. 为什么不是先删缓存再更新数据库？
2. 缓存删除失败怎么办？
3. 缓存穿透、击穿、雪崩分别怎么处理？
4. Spring Cache 和 RedisTemplate 有什么区别？

### 4.5 AOP 自动填充链路

回答模板：

```text
项目里很多表都有 create_time、update_time、create_user、update_user 这类审计字段。
如果每个新增和修改方法都手动 set，会重复而且容易漏。
所以定义了一个 AutoFill 注解，在 Mapper 方法上标记当前是 INSERT 还是 UPDATE。
AOP 切面拦截带注解的 Mapper 方法，通过反射调用实体对象的 setter 方法，把当前时间和当前用户 id 填进去。
这个设计的好处是把公共字段填充从业务代码里抽出来，减少重复代码。
```

可追问点：

1. 为什么切在 Mapper 层而不是 Service 层？
2. 反射有什么性能和安全问题？
3. 如果实体没有对应 setter 会怎样？
4. MyBatis Plus 的自动填充和这个有什么区别？

## 5. 高频项目面试题

### 5.1 你这个项目有哪些模块？

回答：

```text
从业务上分为管理端和用户端。
管理端包括员工、分类、菜品、套餐、订单管理、经营报表、工作台统计和店铺状态；
用户端包括微信登录、地址簿、购物车、菜品套餐查询、下单、支付、订单查询、取消订单和催单。
从代码结构上分为 sky-common、sky-pojo、sky-server 三个 Maven 模块。
common 放通用能力，pojo 放 DTO/VO/Entity，server 放 Controller、Service、Mapper 和配置类。
```

### 5.2 为什么要分 DTO、VO、Entity？

回答：

```text
Entity 对应数据库表结构，主要用于持久化；
DTO 是前端传给后端的请求数据，代表输入；
VO 是后端返回给前端的展示数据，代表输出。
三者分开可以避免数据库字段直接暴露给前端，也能让接口入参和返回值更清晰。
比如下单时前端传 OrdersSubmitDTO，里面是地址 id、备注、餐具数量等；
后端返回 OrderSubmitVO，只需要返回订单 id、订单号、金额、下单时间，不需要把订单表所有字段都返回。
```

### 5.3 统一返回 Result 有什么好处？

回答：

```text
统一返回能让前端处理更简单。
不管哪个接口，都按照 code、msg、data 这种结构返回。
成功时 code 表示成功，data 放业务数据；
失败时 code 表示失败，msg 放错误信息。
这样前端不用为每个接口单独猜返回格式，也方便统一拦截登录过期、权限不足和业务错误。
```

### 5.4 全局异常处理怎么讲？

回答：

```text
业务层遇到错误时不要直接返回字符串，而是抛出业务异常，比如购物车为空、地址不存在、账号锁定。
全局异常处理器用 @RestControllerAdvice 和 @ExceptionHandler 捕获这些异常，再转换成统一 Result 返回给前端。
这样 Controller 和 Service 不需要到处 try-catch，错误返回格式也一致。
```

### 5.5 JWT 鉴权有什么缺点？

回答：

```text
JWT 的优点是无状态，服务端不需要保存 session，适合分布式系统。
缺点是签发后默认无法主动失效，除非设置较短过期时间、引入黑名单或配合 Redis 保存 token 状态。
另外 JWT 只是编码和签名，不是加密，payload 里不能放密码、手机号等敏感信息。
```

### 5.6 ThreadLocal 在项目里有什么风险？

回答：

```text
项目用 ThreadLocal 保存当前用户 id，方便 Service 层获取。
风险在于 Web 容器线程池会复用线程，如果请求结束后不 remove，下一次请求可能读到上一次的数据。
生产代码里应该在拦截器 afterCompletion 或 finally 中清理 ThreadLocal。
```

### 5.7 下单为什么要事务？

回答：

```text
下单不是单表操作。
它至少包括插入订单主表、插入订单明细、清空购物车，后续还可能包括扣库存、优惠券核销、积分处理。
这些操作必须保持一致。
如果订单主表插入成功，但订单明细插入失败，用户就会看到一个没有商品的订单。
所以应该在 Service 方法上加 @Transactional，让这些数据库操作在同一个事务里提交或回滚。
```

### 5.8 订单号怎么设计更合理？

回答：

```text
当前学习项目里可以用时间戳快速生成订单号，但生产环境不够稳。
因为高并发下同一毫秒可能有多个订单，时间戳会重复；同时纯时间戳也容易被猜测。
更合理的方案可以是时间戳 + 机器号 + 随机数，或者使用雪花算法。
如果业务要求订单号可读，也可以按日期前缀加递增序列，但要解决并发生成的问题。
```

### 5.9 WebSocket 的 sessionMap 为什么要改？

回答：

```text
当前代码里 WebSocket 会话放在静态 HashMap 中。
HashMap 不是线程安全的，而 WebSocket 连接建立、断开、发送消息可能由不同线程并发执行。
生产环境应该改成 ConcurrentHashMap，并且发送消息时要处理 session 已关闭、发送失败、异常移除等情况。
如果部署多台实例，还需要把消息通过 Redis Pub/Sub、MQ 或专门的 WebSocket 网关转发到持有连接的节点。
```

### 5.10 为什么说这个项目还不是生产级？

回答：

```text
它已经有比较完整的业务链路，但生产级还需要补很多能力：
第一，关键写操作要补事务和幂等，比如下单、支付回调、取消订单；
第二，缓存需要统一 key、TTL 和一致性策略；
第三，要补充参数校验、接口限流、日志 traceId、异常告警；
第四，要补单元测试和接口测试；
第五，WebSocket 会话、支付回调、文件上传这些点要考虑多实例部署和失败重试。
```

这个回答的好处是：你没有夸大项目，但体现了工程判断。

## 6. 项目亮点怎么讲

### 6.1 亮点一：订单状态流转

可以说：

```text
我把订单状态看成一个状态机，而不是简单字段更新。
订单从待支付、待接单、已接单、派送中、已完成、已取消按业务动作流转。
每个接口只允许在特定状态下操作，比如待支付可以取消，待接单可以接单或拒单，派送中可以完成。
如果不做状态校验，就可能出现已完成订单被取消、未支付订单被接单这类业务错误。
```

### 6.2 亮点二：公共字段自动填充

可以说：

```text
我用自定义注解 + AOP 把审计字段填充抽成公共能力。
业务代码只关心新增或修改本身，不需要重复设置 createTime、updateTime、createUser、updateUser。
这体现的是横切关注点的处理方式，和日志、权限、事务类似。
```

### 6.3 亮点三：缓存一致性思考

可以说：

```text
项目里不是所有数据都适合缓存。
我会优先缓存读多写少、允许短暂不一致的数据，比如分类、套餐、菜品列表和店铺状态。
更新时先改数据库再删除缓存。
对于一致性要求更高的数据，比如订单状态和支付状态，我不会简单缓存，除非有明确的失效和校验策略。
```

## 7. 项目不足和改进方案

| 不足 | 风险 | 改进方案 |
| --- | --- | --- |
| 下单方法缺少事务 | 主表、明细、购物车可能不一致 | 在 Service 层加 `@Transactional` |
| 订单号用时间戳 | 并发下可能重复 | 使用雪花算法或时间戳 + 随机数 |
| 支付模拟成功 | 不符合真实支付流程 | 使用服务端回调、验签、幂等 |
| WebSocket 使用 HashMap | 并发不安全 | 改 ConcurrentHashMap，处理断连和多实例 |
| 缓存 key 分散 | 不易维护 | 统一 RedisKey 常量和命名规范 |
| 参数校验不足 | 脏数据进入业务层 | 使用 Bean Validation |
| 测试不足 | 改动容易回归 | 补充 Service 单元测试和接口测试 |
| 日志不系统 | 排查困难 | 增加 traceId、关键业务日志和异常告警 |

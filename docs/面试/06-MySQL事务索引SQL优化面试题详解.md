## 2. 事务的 ACID 是什么？

### 答案

ACID 是事务的四个特性：

1. Atomicity 原子性：事务内操作要么都成功，要么都失败。
2. Consistency 一致性：事务执行前后数据满足业务约束。
3. Isolation 隔离性：多个事务并发执行时互不干扰到一定程度。
4. Durability 持久性：事务提交后数据持久保存。

### 项目联系

下单链路需要事务。订单主表、订单明细、购物车清空必须作为一个整体：

```text
插入订单主表 -> 插入订单明细 -> 清空购物车
```

如果没有事务，订单主表插入成功但明细失败，就会出现脏订单。

## 3. MySQL 隔离级别有哪些？

### 答案

| 隔离级别 | 脏读 | 不可重复读 | 幻读 |
| --- | --- | --- | --- |
| Read Uncommitted | 可能 | 可能 | 可能 |
| Read Committed | 避免 | 可能 | 可能 |
| Repeatable Read | 避免 | 避免 | InnoDB 下大多可避免 |
| Serializable | 避免 | 避免 | 避免 |

MySQL InnoDB 默认隔离级别通常是 Repeatable Read。

### 概念解释

脏读：读到别的事务还没提交的数据。  
不可重复读：同一事务内两次读同一行，结果不同。  
幻读：同一事务内两次范围查询，第二次出现了第一次没有的行。

### 面试注意

不要只背表格。要能举例：

```text
事务 A 查询某个用户订单数是 10。
事务 B 插入一条新订单并提交。
事务 A 再查同一范围，如果看到 11，就像出现了一条幻影记录，这就是幻读问题。
```

## 4. MVCC 是什么？

### 答案

MVCC 是多版本并发控制。它通过保存数据的多个版本，让读操作尽量不阻塞写操作，写操作也尽量不阻塞读操作，从而提高并发性能。

### InnoDB 中的关键概念

1. 隐藏字段：记录创建事务 id、删除/更新事务 id 等版本信息。
2. undo log：保存历史版本。
3. Read View：一致性读视图，决定当前事务能看到哪些版本。

### 讲解

普通快照读不会直接加锁，而是根据 Read View 判断哪个版本对当前事务可见。如果最新版本不可见，就沿着 undo log 找历史版本。

### 当前读和快照读

快照读：

```sql
select * from orders where id = 1;
```

当前读：

```sql
select * from orders where id = 1 for update;
update orders set status = 2 where id = 1;
```

当前读读的是最新数据，并且可能加锁。

## 5. 索引为什么能加速查询？

### 答案

索引本质是额外的数据结构，帮助数据库快速定位数据。如果没有索引，数据库可能要全表扫描；有索引后，可以通过 B+ 树等结构快速缩小查询范围。

### 讲解

没有索引：

```text
从第一行扫到最后一行，逐行判断 username 是否等于目标值。
```

有索引：

```text
先在 username 索引树上快速定位，再找到对应记录。
```

### 代价

索引不是越多越好：

1. 占磁盘空间。
2. 插入、更新、删除时要维护索引。
3. 优化器可能选择错误索引。
4. 低区分度字段索引效果差。

## 6. B+ 树为什么适合数据库索引？

### 答案

B+ 树适合数据库索引，因为它层级低、磁盘 IO 少、范围查询友好。

### 讲解

特点：

1. 非叶子节点主要存 key 和指针，不存完整数据，一页能放更多 key。
2. 树高度较低，查找时磁盘 IO 次数少。
3. 叶子节点通过链表相连，适合范围查询。
4. 数据有序，支持排序和范围扫描。

### 为什么不用红黑树？

红黑树是二叉树，数据量大时高度比 B+ 树高很多，磁盘 IO 次数更多。数据库索引更关心减少磁盘 IO，而不是单纯内存中的比较次数。

## 7. 聚簇索引和非聚簇索引是什么？

### 答案

InnoDB 中主键索引是聚簇索引，叶子节点存完整行数据。普通二级索引是非聚簇索引，叶子节点存索引列和主键值。

### 回表

如果使用普通索引查到了主键，但查询字段不在该索引里，就需要再根据主键回到聚簇索引查完整行，这叫回表。

示例：

```sql
select name from dish where category_id = 10;
```

如果只有 `category_id` 索引，而 `name` 不在索引里，就可能需要回表。

## 8. 什么是覆盖索引？

### 答案

覆盖索引是指查询需要的字段都能从索引中获取，不需要回表。

示例：

```sql
select id, name from dish where category_id = 10;
```

如果有联合索引：

```sql
(category_id, id, name)
```

查询字段都在索引中，就可能形成覆盖索引。

### 好处

减少回表，提高查询性能。

### 注意

不要为了覆盖所有查询建立特别宽的索引。索引越宽，维护成本越高，占用空间越大。

## 9. 联合索引和最左前缀原则是什么？

### 答案

联合索引是多个字段组成的索引，比如 `(user_id, status, order_time)`。最左前缀原则是指查询条件要从索引最左边的字段开始连续使用，索引才能充分发挥作用。

### 示例

索引：

```sql
idx_user_status_time(user_id, status, order_time)
```

能较好使用：

```sql
where user_id = ?;
where user_id = ? and status = ?;
where user_id = ? and status = ? and order_time between ? and ?;
```

不能充分使用：

```sql
where status = ?;
where order_time between ? and ?;
```

### 面试扩展

联合索引字段顺序要根据查询模式设计。一般把等值查询字段放前面，范围查询字段放后面，同时考虑字段区分度和排序需求。

## 10. 哪些情况会导致索引失效？

### 答案

常见情况：

1. 对索引列使用函数。
2. 对索引列进行计算。
3. 字符串不加引号导致隐式转换。
4. like 以 `%` 开头。
5. 联合索引不满足最左前缀。
6. or 条件中部分字段没有索引。
7. 查询返回数据太多，优化器认为全表扫描更划算。

### 示例

索引失效：

```sql
where date(create_time) = '2026-07-17'
```

更好：

```sql
where create_time >= '2026-07-17 00:00:00'
  and create_time <  '2026-07-18 00:00:00'
```

## 11. explain 主要看什么？

### 答案

常看字段：

1. type：访问类型，是否全表扫描。
2. possible_keys：可能使用的索引。
3. key：实际使用的索引。
4. rows：预估扫描行数。
5. Extra：额外信息，比如 Using index、Using where、Using filesort、Using temporary。

### type 大致好坏

```text
system/const > eq_ref > ref > range > index > ALL
```

`ALL` 通常表示全表扫描，要重点关注。

### Extra 常见含义

1. Using index：可能使用覆盖索引。
2. Using where：server 层继续过滤。
3. Using filesort：需要额外排序，不一定真的写文件，但通常要关注。
4. Using temporary：使用临时表，通常要关注。

## 12. 慢 SQL 怎么排查？

### 答案

排查步骤：

1. 确认慢 SQL：慢日志、APM、接口日志。
2. 看执行计划：`explain` 分析索引、扫描行数、排序、临时表。
3. 看 SQL 写法：是否 select *、是否函数计算、是否大分页、是否 N+1。
4. 看索引：是否缺索引、索引顺序是否合理、是否低区分度。
5. 看数据量和表结构：是否需要归档、分表、冗余字段。
6. 看锁等待：是否被事务阻塞。
7. 优化后压测验证，不要只看单次执行。

### 项目联系

订单列表按用户、状态、时间分页查询时，可以考虑联合索引：

```sql
(user_id, status, order_time)
```

如果管理端按手机号、订单号、时间范围搜索，则要根据实际查询频率设计不同索引，避免一个大而全索引解决所有问题。

## 13. 大分页为什么慢？怎么优化？

### 答案

大分页慢是因为：

```sql
limit 100000, 10
```

数据库需要先扫描并丢弃前 100000 行，再返回 10 行。offset 越大，成本越高。

### 优化方式

1. 基于上次最大 id 翻页：

```sql
select * from orders
where id > ?
order by id
limit 10;
```

2. 延迟关联：

```sql
select o.*
from orders o
join (
    select id from orders order by id limit 100000, 10
) t on o.id = t.id;
```

3. 限制最大页数。
4. 搜索条件尽量精准。
5. 使用游标分页。

## 14. MySQL 锁有哪些？

### 答案

按粒度：

1. 表锁。
2. 行锁。

InnoDB 常见：

1. 记录锁：锁某条索引记录。
2. 间隙锁：锁索引记录之间的间隙。
3. 临键锁：记录锁 + 间隙锁。

按模式：

1. 共享锁：读锁。
2. 排他锁：写锁。

### 注意

InnoDB 行锁是基于索引实现的。如果条件没有走索引，可能锁住更多行，甚至造成类似表锁的效果。

## 15. 什么是间隙锁？

### 答案

间隙锁锁的是索引记录之间的范围，目的是防止其他事务在范围内插入新记录，从而避免幻读。

示例：

```sql
select * from orders
where id between 10 and 20
for update;
```

在一定隔离级别和索引条件下，InnoDB 可能不仅锁住已有记录，还锁住 10 到 20 之间的间隙，防止别人插入新 id。

### 面试注意

间隙锁容易导致并发插入阻塞。设计事务时要尽量缩小锁范围，确保查询走索引，并避免长事务。

## 16. 死锁怎么产生？怎么处理？

### 答案

死锁通常是两个事务按不同顺序持有和等待资源。

示例：

```text
事务 A 锁订单 1，再锁订单 2。
事务 B 锁订单 2，再锁订单 1。
两者互相等待，形成死锁。
```

处理方式：

1. 固定资源访问顺序。
2. 缩短事务时间。
3. 确保 SQL 走索引，减少锁范围。
4. 避免事务中调用外部接口。
5. 捕获死锁异常后按业务允许进行重试。

## 17. 订单表如何设计索引？

### 答案

根据查询场景设计，而不是盲目加索引。

用户端常见查询：

```sql
where user_id = ?
order by order_time desc
limit ?, ?
```

可以考虑：

```sql
(user_id, order_time)
```

按状态筛选：

```sql
where user_id = ? and status = ?
order by order_time desc
```

可以考虑：

```sql
(user_id, status, order_time)
```

管理端按订单号查询：

```sql
where number = ?
```

可以给订单号加唯一索引或普通索引，取决于业务是否保证唯一。

### 注意

1. 不要给每个字段都加索引。
2. 低区分度字段单独建索引意义不大，比如性别、简单状态。
3. 联合索引要结合 where、order by、select 字段设计。
4. 写多的表索引过多会拖慢写入。

## 18. 数据库表设计面试怎么答？

### 答案结构

1. 先说核心实体。
2. 再说关系。
3. 再说关键字段。
4. 再说索引。
5. 最后说一致性和扩展。

以订单为例：

```text
订单主表保存订单级信息，比如订单号、用户 id、地址、金额、状态、支付状态、下单时间。
订单明细表保存每个菜品或套餐的快照信息，比如名称、数量、金额、图片、口味。
二者是一对多关系，订单明细通过 order_id 关联订单主表。
这样设计的原因是一个订单可能包含多个商品，且商品名称和价格后续可能变化，所以订单明细要保存下单时快照。
```

## 19. 为什么订单明细要保存商品快照？

### 答案

因为订单是历史事实。用户下单时的商品名称、价格、口味、图片应该保持不变。即使商家后来修改菜品价格或名称，历史订单也不能跟着变化。

所以订单明细表通常保存冗余字段：

1. 商品名称。
2. 商品图片。
3. 商品单价。
4. 数量。
5. 口味。

这是一种合理冗余，用来保证历史数据稳定。

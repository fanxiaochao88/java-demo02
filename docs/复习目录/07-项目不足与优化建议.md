# 07 - 项目不足与优化建议

## 1. 先说结论

这个项目能跑通完整业务，学习价值很高。
但从“可维护性”和“后续项目扩展”角度看，还有一些明显可以优化的地方。

## 2. 优先级最高的优化

| 问题 | 影响 | 建议 |
|---|---|---|
| `WebMvcConfiguration` 继承 `WebMvcConfigurationSupport` | 会接管 Spring Boot 默认 MVC 配置 | 如果只是加拦截器和转换器，优先考虑 `WebMvcConfigurer` |
| Admin/User 拦截器代码重复 | 后续维护成本高 | 抽一个公共鉴权模板或公共工具方法 |
| `allow-circular-references: true` | 掩盖循环依赖问题 | 逐步拆掉循环依赖，恢复默认约束 |
| `WebSocketServer` 用静态 `HashMap` | 并发场景不安全 | 改成 `ConcurrentHashMap` |
| `GlobalExceptionHandler` 解析重复键错误靠字符串 | 不够稳 | 封装更明确的异常处理逻辑 |

## 3. 中优先级优化

| 问题 | 影响 | 建议 |
|---|---|---|
| `AliOssUtil` 和 COS 同时存在 | 容易让人误判主线 | 保留一个主存储方案，另一个明确标注为历史实现 |
| `ShoppingCutController` 命名不规范 | 阅读成本高 | 统一命名为 `ShoppingCartController` 更清晰 |
| 业务里 magic number 较多 | 可读性一般 | 把状态值继续集中到常量或枚举 |
| 日志和异常信息风格不完全统一 | 排查问题时不够整齐 | 统一日志模板和错误码规范 |

## 4. 代码层面的具体建议

### 4.1 统一登录鉴权

现在的管理员和用户拦截器本质上逻辑相同，只是：

- token 名不同
- secret 不同
- claims 键不同

后续可以把“解析 token + 取当前 id”的逻辑抽成公共方法。

### 4.2 减少反射成本

`AutoFillAspect` 通过反射调用 setter，学习价值高，但生产里可以继续优化：

- 缓存 Method
- 或者改成更显式的数据填充方案

### 4.3 订单状态统一表达

`Orders` 里已经有常量，但业务代码里仍然容易直接写数字。
建议后续继续推进：

- 常量集中化
- 或者改成枚举表达状态

### 4.4 提高并发安全

`WebSocketServer` 的 session 存储建议用线程安全容器：

```java
private static final Map<String, Session> sessionMap = new ConcurrentHashMap<>();
```

## 5. 学习层面的优化

如果你接下来做新项目，建议直接按这个顺序复习：

1. 先画架构图
2. 再画登录链路
3. 再画下单链路
4. 再画报表和实时通知链路
5. 最后回头看 Java 语法和注解

这样你会从“背代码”变成“看设计”。

## 6. 这套项目最值得保留的地方

- 分层清晰
- 主流程完整
- 技术点覆盖广
- 适合做二次复盘

也就是说，它适合当“毕业复盘项目”，不适合当“无脑抄完就扔”的项目。

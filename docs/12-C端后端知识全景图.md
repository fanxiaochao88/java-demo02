## 1. B 端 vs C 端：本质差异

```
┌─────────────────────────────────────────────────────────────────────┐
│                                                                      │
│   B 端（企业内部）                        C 端（面向消费者）            │
│   ┌─────────────────┐                   ┌─────────────────┐          │
│   │ 用户量：几百/几千 │                   │ 用户量：百万/亿级 │          │
│   │ 并发：几十 QPS    │                   │ 并发：万级/十万级  │          │
│   │ 数据量：几万条    │                   │ 数据量：百亿级    │          │
│   │ 业务：流程审批    │                   │ 业务：秒杀/支付   │          │
│   │ 可用性：99% 就行  │                   │ 可用性：99.99%    │          │
│   │ SLA：挂了重启     │                   │ SLA：挂了赔钱     │          │
│   └─────────────────┘                   └─────────────────┘          │
│                                                                      │
│   你之前做的                           你现在要学的                     │
│                                                                      │
└─────────────────────────────────────────────────────────────────────┘
```

| 维度 | B 端（企业管理） | C 端（电商/外卖） |
|------|-----------------|-------------------|
| **核心技术瓶颈** | 业务逻辑复杂度 | 并发、性能、稳定性 |
| **数据库设计** | 表单结构清晰，关系明确 | 高并发读写，需要分库分表 |
| **缓存** | 可有可无 | **必须**，Redis 是标配 |
| **消息队列** | 一般用不到 | 削峰填谷、解耦异步 |
| **分布式** | 单机搞定 | 集群、微服务、注册中心 |
| **事务** | 单库事务足够 | 分布式事务（Seata / 消息最终一致性） |
| **安全** | 内网，关注点少 | 接口防刷、数据脱敏、支付安全 |
| **日志/监控** | 查数据库就行 | ELK、Prometheus、链路追踪 |
| **CI/CD** | 手动发布 | 自动化灰度、蓝绿部署 |

> 但别被吓到——**每个 C 端大佬都是从 CRUD 开始的**。你现在的苍穹外卖项目就是最好的起点。

## 2. C 端后端的核心挑战

用一个电商场景串起来：

```
 双11零点秒杀

 1亿用户同时刷新页面  ──→  缓存雪崩怎么办？
      │
      ▼
 100万人同时下单     ──→  库存扣减不准？数据库扛得住吗？
      │
      ▼
 10万人同时支付      ──→  支付超时怎么处理？幂等怎么做？
      │
      ▼
 仓库/物流           ──→  如何保证订单状态一致？
      │
      ▼
 退款/售后           ──→  资金安全、逆向流程
```

**一句话：C 端的难，不在功能多，而在"人太多了"。**

### 3.1 缓存体系

> **一句话：内存比磁盘快 10 万倍。把热点数据放内存，是 C 端性能的基础。**

```
请求 → Redis（命中） → 返回      （1ms）
请求 → Redis（未命中） → MySQL → 写回Redis → 返回    （50ms+）
```

| 知识点 | 是什么 | 典型场景 |
|--------|--------|---------|
| **缓存穿透** | 恶意查不存在的数据，缓存不生效 | 布隆过滤器、缓存空值 |
| **缓存击穿** | 热点 key 过期瞬间，大量请求打 DB | 互斥锁、永不过期 |
| **缓存雪崩** | 大量 key 同时过期，DB 瞬间崩溃 | 过期时间加随机值、多级缓存 |
| **双写一致性** | 更新 DB 后，缓存怎么同步？ | 先删缓存再更新 DB、Canal 订阅 binlog |
| **多级缓存** | Caffeine(本地) → Redis(分布式) → DB | 秒杀商品详情 |

**你在苍穹外卖已经做了：** Redis 缓存菜品分类（第6天的内容），这是缓存的入门用法。

### 3.2 消息队列

> **一句话：让系统各模块异步通信，不用傻等。削峰填谷，保护数据库。**

```
同步模式（不用MQ）：
  下单 → 扣库存 → 发短信 → 发优惠券 → 返回
  用户要等所有步骤完成才能看到"下单成功"

异步模式（用MQ）：
  下单 → 发MQ消息 → 返回（快！）
              ↓
         ┌────┼────┐
         ▼    ▼    ▼
       扣库存 发短信 发优惠券
```

| 消息队列 | 特点 | 适用场景 |
|---------|------|---------|
| **RabbitMQ** | 功能全面，社区活跃 | 业务解耦、延迟消息 |
| **RocketMQ** | 阿里出品，事务消息 | 电商交易、分布式事务 |
| **Kafka** | 超高吞吐，日志流处理 | 用户行为埋点、实时分析 |

| 核心概念 | 说明 |
|---------|------|
| **削峰填谷** | 流量尖峰写入 MQ，消费者平滑拉取 |
| **顺序消息** | 同一个订单的消息按顺序消费（如：先创建→再支付→后发货） |
| **死信队列** | 消费失败的消息进入死信，人工处理 |
| **延迟消息** | 下单30分钟后未支付 → 自动取消（RocketMQ 18个延迟级别） |

### 3.3 分布式系统

> **一句话：一台机器扛不住了，用多台一起干，但"多台一起"会引入新问题。**

```
单体（你现在的苍穹外卖）：
  ┌────────────────────────┐
  │  一台服务器跑所有代码    │
  │  Controller + Service  │
  │  + Mapper（一个jar包）  │
  └────────────────────────┘

微服务（C端常见）：
  ┌────────┐ ┌────────┐ ┌────────┐ ┌────────┐
  │ 用户服务 │ │ 订单服务 │ │ 商品服务 │ │ 支付服务 │
  │ :8081   │ │ :8082   │ │ :8083   │ │ :8084   │
  └────────┘ └────────┘ └────────┘ └────────┘
       各自独立部署、独立数据库、独立扩容
```

| 新问题 | 解决方案 |
|--------|---------|
| 服务怎么互相找到？ | **注册中心**（Nacos / Eureka） |
| 配置怎么统一管理？ | **配置中心**（Nacos / Apollo） |
| 一个服务挂了怎么办？ | **熔断降级**（Sentinel / Hystrix） |
| 跨服务事务怎么保证？ | **分布式事务**（Seata / 消息最终一致性） |
| 并发竞争资源怎么办？ | **分布式锁**（Redis Redisson / ZooKeeper） |
| ID 怎么全局唯一？ | **分布式 ID**（雪花算法 / 美团 Leaf） |

> **注意：** 微服务不是银弹。用户量不到百万级的项目，单体 + 模块化就够了。**不要为了微服务而微服务。**

### 3.4 数据库进阶

> **一句话：当一张表几千万行、每秒几千次写入时，单库单表就扛不住了。**

```
纵向扩展（单机升级）：
  4核8G → 8核16G → 16核32G → ... → 到头了，物理上限

横向扩展（分库分表）：
  orders 表 → orders_0, orders_1, orders_2, orders_3
  每个表的行数 = 原来的 1/4，性能翻倍
```

| 技术 | 解决的问题 |
|------|-----------|
| **读写分离** | 读多写少，主库写、从库读 |
| **分库分表** | 单表数据量过大（ShardingSphere / MyCat） |
| **慢SQL优化** | `EXPLAIN` 分析、索引覆盖、避免回表 |
| **连接池调优** | Druid/HikariCP 参数调优 |

```
分库分表示例：
  按 userId % 4 分库：
    用户1,5,9 → DB0
    用户2,6,10 → DB1
    用户3,7,11 → DB2
    用户4,8,12 → DB3

  按时间分区：
    orders_202601, orders_202602, orders_202603 ...
```

### 3.5 并发编程

> **一句话：多个请求同时操作同一份数据时，保证不出错。**

```java
// 秒杀场景：1000人同时抢 100 件商品

// ❌ 错误写法
public void seckill(Long productId) {
    Product p = productMapper.selectById(productId);
    if (p.getStock() > 0) {
        p.setStock(p.getStock() - 1);
        productMapper.updateById(p);  // 超卖！100件可能卖出150件
    }
}

// ✅ 正确写法思路
// 1. Redis 预扣库存
// 2. 数据库乐观锁 UPDATE ... SET stock = stock - 1 WHERE stock > 0
// 3. 消息队列异步创建订单
```

| 知识点 | 用途 |
|--------|------|
| **线程池** | 控制并发数量，避免无限创建线程 |
| **synchronized** | 单机互斥 |
| **ReentrantLock** | 更灵活的锁，可中断、可超时 |
| **CompletableFuture** | 异步编排，并行调用多个服务 |
| **CountDownLatch / CyclicBarrier** | 多线程协调 |
| **ConcurrentHashMap** | 高并发 Map |

### 3.6 系统安全

> **一句话：C 端系统暴露在公网，谁都能访问，所以安全是底线。**

| 安全点 | 问题 | 解决方案 |
|--------|------|---------|
| **接口防刷** | 1秒刷100次登录 | 限流（令牌桶、漏桶）、验证码 |
| **接口幂等** | 用户连点两次"下单"按钮 | 唯一请求号、数据库唯一约束 |
| **数据脱敏** | 日志里打出了手机号/密码 | `138****8888`，敏感字段 @JsonIgnore |
| **支付安全** | 金额被篡改 | 服务端重新计算金额，不信任前端传来的 |
| **SQL注入** | `' OR '1'='1'` | MyBatis `#{}` 不用 `${}` |
| **XSS攻击** | 评论里注入脚本 | HTML 转义 |
| **CSRF攻击** | 伪造请求 | Token 校验 |

### 3.8 架构设计

> **一句话：CRUD 写多了，你需要更高层次的思考——怎么组织代码更清晰、更易维护。**

| 方法/模式 | 核心思想 | 你什么时候可以学 |
|----------|---------|----------------|
| **DDD 领域驱动设计** | 代码按业务领域拆分，而不是按技术层 | 做了 2-3 个业务系统后 |
| **事件驱动架构** | 通过事件传递状态变化，解耦模块 | 理解消息队列后 |
| **CQRS** | 读写分离，写用关系型，读用 ES | 遇到复杂查询需求时 |
| **设计模式** | 策略、观察者、模板、责任链... | 随时可以，你现在就在用 |
| **整洁架构** | 业务核心不依赖框架 | 做中大型项目时 |

### 3.9 业务专题（电商/外卖核心）

| 业务领域 | 核心难点 | 关键技术 |
|---------|---------|---------|
| **订单状态机** | 多状态流转，不能乱跳 | 状态守卫、乐观锁、事件通知 |
| **支付系统** | 不掉单、不重复扣款、退款对账 | 支付回调、幂等、对账文件 |
| **库存系统** | 不超卖、不少卖、实时准确 | Redis 预扣、DB 乐观锁、对账 |
| **优惠券系统** | 发放/核销/过期、防刷 | 分布式锁、定时任务 |
| **秒杀系统** | 瞬间高并发、页面静态化 | Redis + Lua、MQ 削峰、CDN |
| **对账系统** | 我方账单 vs 支付宝账单，分毫不差 | 定时任务、差异告警 |

**学习原则：**

1. **别跳级。** 单体没玩明白就去搞微服务，只会更懵。
2. **每个阶段找一个项目练手。** 学了不用 = 没学。
3. **优先学"工作中用得到的"。** Kafka 很牛，但你们公司用 RabbitMQ 就先学 RabbitMQ。
4. **面试加分项可以单独突击。** JUC、JVM、算法这些是面试硬通货。

## 6. 总结

```
B 端是 Java 的"工业应用"——稳定、规范、业务驱动
C 端是 Java 的"军事演习"——高并发、高可用、技术驱动

你现在做的苍穹外卖 = Java 后端入门的"标准教材"
它带着你把 Spring Boot + MyBatis + Redis + 微信支付 + 订单状态机
从头到尾走了一遍，这个基础打好了，后面学分布式的每一步都有"锚点"。

不要急着一步登天，一个外卖项目吃透，比囫囵吞枣学 10 个
微服务框架强得多。
```

> **你接下来的节奏：** 把苍穹外卖的订单模块写完 → 理解状态机 → 接入支付 → 完成整个交易闭环。做完这些，你就拥有一个完整的 C 端单体项目经验了。之后再往中间件和分布式方向走，每一步都会很踏实。

## 1. 从购物车结算说起

你现在的进度是：购物车增删改查已经完成。当用户点击"去结算"按钮时，业务流程是这样的：

```
购物车 → 点击结算 → 填写地址/备注 → 提交订单 → 进入订单模块
                                                    ↓
                                        订单状态 = 1 (待付款)
                                                    ↓
                                        用户付款 → 状态变为 2 (待接单)
                                                    ↓
                                        商家接单 → 状态变为 3 (已接单)
                                                    ↓
                                        骑手配送 → 状态变为 4 (派送中)
                                                    ↓
                                        确认收货 → 状态变为 5 (已完成)
```

这就是一个典型的**订单生命周期**，而管理这个生命周期的机制就叫**状态机**。

> 在本项目中，"点击结算"对应的操作是调用 `POST /user/order/submit` 接口，传入 `OrdersSubmitDTO`（包含地址ID、支付方式、备注等），服务器创建订单并将状态设为 `1 (待付款)`。

## 2. 什么是状态机

### 2.1 直观理解

**状态机 = 状态 + 转换规则**

想象一个红绿灯：

```
     ┌──────────────────────────────────┐
     │                                  │
     ▼                                  │
   🟢 绿灯 ──→ 🟡 黄灯 ──→ 🔴 红灯 ──→ 🟢
```

- **状态**：绿灯、黄灯、红灯（3 种状态）
- **转换**：绿灯只能变成黄灯，黄灯只能变成红灯，红灯只能变成绿灯
- **非法转换**：绿灯不能直接变成红灯（必须先经过黄灯）

订单也是同理：**待付款**不能直接跳到**已完成**，必须经过中间的合法步骤。

### 2.2 教科书定义

> 状态机（State Machine / Finite State Machine, FSM）是一种数学模型，描述一个对象在其生命周期中可能处于的各种状态，以及在接收到特定事件时如何从一个状态转移到另一个状态。

三个核心要素：

| 要素 | 含义 | 订单场景举例 |
|------|------|-------------|
| **状态 (State)** | 对象当前所处的阶段 | 待付款、待接单、已接单... |
| **事件 (Event)** | 触发状态变化的行为 | 用户付款、商家接单、骑手取餐... |
| **转换 (Transition)** | 从一个状态到另一个状态 | 待付款 —(付款)→ 待接单 |

### 2.3 简单代码类比

```java
// 没有状态机思想的代码（坏味道）
if (order.getStatus() == 1) {
    // 待付款的处理...
} else if (order.getStatus() == 2) {
    // 待接单的处理...
} else if (order.getStatus() == 6) {
    // 取消的处理... 等等，已取消的订单能直接变成已完成吗？
}

// 有状态机思想的代码
public void pay(Long orderId) {
    Order order = getOrder(orderId);
    if (order.getStatus() != PENDING_PAYMENT) {  // 只有待付款才能付款
        throw new OrderBusinessException("订单状态不允许付款");
    }
    order.setStatus(TO_BE_CONFIRMED);  // 付完款变成待接单
    updateOrder(order);
}
```

**区别在哪？** 状态机代码明确规定了**哪些转换是合法的**，避免了"已取消订单莫名其妙变成已完成"这种逻辑错误。

## 3. 苍穹外卖的订单状态定义

本项目已经在 `Orders` 实体中定义了完整的订单状态常量。来看看源码：

**文件位置：** `sky-pojo/src/main/java/com/sky/entity/Orders.java`

### 3.1 订单状态（6 种）

```java
public class Orders implements Serializable {
    // 1. 待付款 —— 用户刚提交订单，还没付钱
    public static final Integer PENDING_PAYMENT = 1;

    // 2. 待接单 —— 用户付完款了，等待商家确认
    public static final Integer TO_BE_CONFIRMED = 2;

    // 3. 已接单 —— 商家确认了订单，准备出餐
    public static final Integer CONFIRMED = 3;

    // 4. 派送中 —— 骑手已取餐，正在送餐中
    public static final Integer DELIVERY_IN_PROGRESS = 4;

    // 5. 已完成 —— 用户确认收货，订单结束（正常终态）
    public static final Integer COMPLETED = 5;

    // 6. 已取消 —— 订单被取消，订单结束（异常终态）
    public static final Integer CANCELLED = 6;
}
```

### 3.2 支付状态（3 种）

```java
    // 支付状态（独立于订单状态，但有紧密关联）
    public static final Integer UN_PAID = 0;   // 未支付
    public static final Integer PAID = 1;       // 已支付
    public static final Integer REFUND = 2;     // 退款
```

> **注意**：支付状态和订单状态是两个字段，但存在因果关系。比如：
> - `payStatus` 从 `UN_PAID(0)` → `PAID(1)` 会触发 `status` 从 `PENDING_PAYMENT(1)` → `TO_BE_CONFIRMED(2)`
> - `payStatus` 从 `PAID(1)` → `REFUND(2)` 会触发 `status` 变为 `CANCELLED(6)`

## 4. 完整的状态流转图

```
                          用户提交订单
                              │
                              ▼
                    ┌─────────────────┐
                    │   (1) 待付款     │  ◄─── 流程起点
                    │  PENDING_PAYMENT │
                    └────────┬────────┘
                             │
              ┌──────────────┼──────────────┐
              │ 用户付款      │              │ 用户/超时取消
              ▼              │              ▼
    ┌─────────────────┐      │    ┌─────────────────┐
    │  (2) 待接单      │      │    │  (6) 已取消      │
    │  TO_BE_CONFIRMED │      │    │   CANCELLED      │
    └────────┬────────┘      │    └─────────────────┘
             │               │            ▲
     ┌───────┼───────┐       │            │
     │ 商家接单│ 商家拒单│       │    ┌───────┘
     ▼       ▼       │       │    │ 已付款订单
┌─────────┐ ┌─────────────┐ │    │ 用户也可以取消
│(3)已接单│ │  (6) 已取消  │ │    │ (需走退款)
│CONFIRMED│ │  CANCELLED   │ │    │
└────┬────┘ └─────────────┘ │    │
     │                      │    │
     │ 商家出餐完成          │    │
     │ 骑手取餐              │    │
     ▼                      │    │
┌─────────────────┐         │    │
│(4) 派送中        │         │    │
│DELIVERY_IN_      │         │    │
│PROGRESS          │         │    │
└────────┬────────┘         │    │
         │                  │    │
         │ 用户确认收货       │    │
         ▼                  │    │
┌─────────────────┐         │    │
│  (5) 已完成      │         │    │
│   COMPLETED      │         │    │
└─────────────────┘         │    │
    正常终态                 │    │
                            │    │
          两种取消方式 ──────┘────┘
          (未付款直接取消 / 已付款取消并退款)
```

### 4.1 主线流程（快乐路径）

```
(1)待付款 → (2)待接单 → (3)已接单 → (4)派送中 → (5)已完成
   付款       接单       出餐取餐     确认收货
```

### 4.2 取消分支

| 起点状态 | 触发条件 | 是否需退款 | 终态 |
|---------|---------|-----------|------|
| (1) 待付款 | 用户主动取消 / 超时未付 | 否 | (6) 已取消 |
| (2) 待接单 | 用户申请取消 | 是 | (6) 已取消 |
| (2) 待接单 | 商家拒单 | 是 | (6) 已取消 |
| (3) 已接单 | 用户申请取消（协商） | 是 | (6) 已取消 |

### 4.3 非法状态转换示例

```
❌ (1)待付款 → (4)派送中      （没付钱怎么能送？）
❌ (3)已接单 → (1)待付款      （时光不能倒流）
❌ (6)已取消 → (3)已接单      （已取消是终态，不能再转）
❌ (5)已完成 → 任何状态        （已完成是终态，不能再转）
```

> **状态 (5) 已完成** 和 **状态 (6) 已取消** 都是**终态（Terminal State）**，一旦进入就不能再转换到任何其他状态。

## 5. 用户端 vs 商家端视角

同一个订单，用户和商家看到的和能操作的是不一样的：

| 订单状态 | 用户看到的 | 用户能做什么 | 商家看到的 | 商家能做什么 |
|---------|-----------|-------------|-----------|-------------|
| (1) 待付款 | "等待付款" | 去付款 / 取消订单 | "新订单" | 无操作 |
| (2) 待接单 | "已付款，等待商家接单" | 申请退款 | "待接单" | 接单 / 拒单 |
| (3) 已接单 | "商家已接单，正在准备" | 申请退款 | "备餐中" | 完成备餐（触发派送） |
| (4) 派送中 | "骑手正在配送" | 确认收货 | "配送中" | 无操作 |
| (5) 已完成 | "已完成" | 再来一单 / 评价 | "已完成" | 无操作 |
| (6) 已取消 | "已取消" | 再来一单 | "已取消" | 无操作 |

这就是为什么本项目中有两个 controller 包：`controller/user/` 和 `controller/admin/`，分别处理用户端和商家端的操作。

## 6. 每个状态的业务含义

### 6.1 待付款（PENDING_PAYMENT = 1）

```
触发：用户提交订单时自动设置
动作：订单已创建，但还未扣款
倒计时：通常有 15-30 分钟付款倒计时，超时自动取消
库存：已扣减（预占库存），取消后释放
```

核心问题：**创建订单时要不要扣库存？**

```
方案A（预占）：创建订单时扣库存，超时未付释放库存
    ✅ 防止超卖
    ❌ 可能有人恶意占库存

方案B（付款后扣）：付款成功后才扣库存
    ✅ 不会恶意占库存
    ❌ 多用户同时付款可能导致超卖（需要更复杂的锁）
```

本项目中，由于是学习项目，用方案A即可（创建订单时扣减库存）。

### 6.2 待接单（TO_BE_CONFIRMED = 2）

```
触发：用户付款成功
含义：钱已扣，等待商家确认
商家操作：接单 / 拒单
如果拒单：需要退款，状态变为 (6) 已取消
```

### 6.3 已接单（CONFIRMED = 3）

```
触发：商家点击"接单"
含义：商家确认收到订单，开始准备食物
此阶段的取消：需要双方协商，商家同意后才能取消退款
```

### 6.4 派送中（DELIVERY_IN_PROGRESS = 4）

```
触发：商家完成备餐，骑手取餐
含义：食物已在送达途中
用户操作：查看骑手位置、确认收货
此阶段通常不允许取消（餐已经在路上了）
```

### 6.5 已完成（COMPLETED = 5）

```
触发：用户点击"确认收货"
含义：订单正常完成，终态
后续：可能引导用户评价
```

### 6.6 已取消（CANCELLED = 6）

```
触发方式：
  1. 待付款时用户主动取消
  2. 超时未付款系统自动取消
  3. 待接单时商家拒单
  4. 已付款后用户申请退款（需协商）
终态，不可再转换
```

## 7. 为什么要用状态机

### 7.1 不用状态机会怎样？

假设不用状态机逻辑，我们写出这样的代码：

```java
// 恐怖代码：没有状态校验
public void cancelOrder(Long orderId) {
    Order order = orderMapper.getById(orderId);
    order.setStatus(CANCELLED);  // 任何状态都能取消？
    orderMapper.update(order);
}

public void completeOrder(Long orderId) {
    Order order = orderMapper.getById(orderId);
    order.setStatus(COMPLETED);  // 没付款也能完成？
    orderMapper.update(order);
}
```

可能出现的问题：
- 已完成(5)的订单又变成已取消(6)（钱退了但货也收了？）
- 已取消(6)的订单又变成派送中(4)（取消了的订单还在送？）
- 待付款(1)直接变成已完成(5)（没付钱的订单完成了？）

### 7.2 用了状态机的好处

```java
public void cancelOrder(Long orderId) {
    Order order = orderMapper.getById(orderId);

    // 状态机核心：校验是否允许取消
    if (order.getStatus().equals(CANCELLED) || order.getStatus().equals(COMPLETED)) {
        throw new OrderBusinessException("订单已结束，无法取消");
    }
    if (order.getStatus().equals(DELIVERY_IN_PROGRESS)) {
        throw new OrderBusinessException("订单配送中，无法取消");
    }

    order.setStatus(CANCELLED);
    // 如果是已付款的，触发退款
    if (order.getPayStatus().equals(PAID)) {
        refund(order);
    }
    orderMapper.update(order);
}
```

**核心思想：在执行任何操作前，先判断"当前状态是否允许这个操作"。**

## 8. 代码中如何实现状态机

### 8.1 方式一：if-else 守卫（简单场景推荐）

最直接的方式，在每个业务方法开头做状态校验：

```java
@Service
public class OrderServiceImpl implements OrderService {

    @Override
    public void pay(OrdersPaymentDTO paymentDTO) {
        Orders order = orderMapper.getByNumber(paymentDTO.getOrderNumber());

        // 状态守卫：只有待付款才能付款
        if (!order.getStatus().equals(Orders.PENDING_PAYMENT)) {
            throw new OrderBusinessException(MessageConstant.ORDER_STATUS_ERROR);
        }

        // 调用微信支付
        // ...

        // 支付成功 → 变更状态
        order.setStatus(Orders.TO_BE_CONFIRMED);
        order.setPayStatus(Orders.PAID);
        orderMapper.update(order);
    }

    @Override
    public void confirm(OrdersConfirmDTO confirmDTO) {
        Orders order = orderMapper.getById(confirmDTO.getId());

        // 状态守卫：只有待接单才能接单
        if (!order.getStatus().equals(Orders.TO_BE_CONFIRMED)) {
            throw new OrderBusinessException(MessageConstant.ORDER_STATUS_ERROR);
        }

        order.setStatus(Orders.CONFIRMED);
        orderMapper.update(order);
    }

    // ... 同理实现 delivery、complete、cancel 等方法
}
```

### 8.2 方式二：状态转换表（中等复杂度）

定义一个 Map 来声明所有合法转换：

```java
// 声明合法转换：key = 当前状态，value = 允许转换到的状态列表
private static final Map<Integer, List<Integer>> ALLOWED_TRANSITIONS = Map.of(
    Orders.PENDING_PAYMENT,     List.of(Orders.TO_BE_CONFIRMED, Orders.CANCELLED),
    Orders.TO_BE_CONFIRMED,     List.of(Orders.CONFIRMED, Orders.CANCELLED),
    Orders.CONFIRMED,           List.of(Orders.DELIVERY_IN_PROGRESS, Orders.CANCELLED),
    Orders.DELIVERY_IN_PROGRESS, List.of(Orders.COMPLETED)
    // COMPLETED 和 CANCELLED 是终态，没有出口
);

public void transition(Orders order, Integer targetStatus) {
    Integer currentStatus = order.getStatus();
    List<Integer> allowed = ALLOWED_TRANSITIONS.get(currentStatus);

    if (allowed == null || !allowed.contains(targetStatus)) {
        throw new OrderBusinessException(
            String.format("非法状态转换：%d → %d", currentStatus, targetStatus)
        );
    }

    order.setStatus(targetStatus);
    orderMapper.update(order);
}
```

### 8.3 方式三：Spring State Machine 框架（复杂场景）

对于真正的生产项目，可以使用 Spring State Machine 框架：

```java
// 伪代码示意，本项目暂不使用
@Configuration
@EnableStateMachine
public class OrderStateMachineConfig extends StateMachineConfigurerAdapter<Integer, Integer> {

    @Override
    public void configure(StateTransitionConfigurer<Integer, Integer> transitions) {
        transitions
            .withExternal()
                .source(PENDING_PAYMENT).target(TO_BE_CONFIRMED).event(PAY_EVENT)
            .and()
            .withExternal()
                .source(TO_BE_CONFIRMED).target(CONFIRMED).event(CONFIRM_EVENT)
            // ... 以此类推
    }
}
```

> **对本项目建议**：使用**方式一（if-else 守卫）**即可。项目规模不大，6 个状态的管理用 if-else 已经足够清晰，引入框架反而增加复杂度。

## 10. 关键技术点

### 10.1 订单号的生成

不能用自增ID当订单号（太短、可猜测），通常用时间戳+随机数：

```java
// 常见格式：2026062315304512345
private String generateOrderNumber() {
    String datetime = LocalDateTime.now().format(DateTimeFormatter.ofPattern("yyyyMMddHHmmss"));
    String random = String.format("%04d", (int)(Math.random() * 10000));
    return datetime + random;
}
```

### 10.2 创建订单时的数据来源

```java
public OrderSubmitVO submit(OrdersSubmitDTO ordersSubmitDTO) {
    Long userId = BaseContext.getCurrentId();

    // 1. 从购物车获取菜品列表
    List<ShoppingCart> cartList = shoppingCartMapper.list(userId);
    if (cartList == null || cartList.isEmpty()) {
        throw new OrderBusinessException(MessageConstant.SHOPPING_CART_IS_NULL);
    }

    // 2. 从地址簿获取收货地址
    AddressBook addressBook = addressBookMapper.getById(ordersSubmitDTO.getAddressBookId());
    if (addressBook == null) {
        throw new OrderBusinessException(MessageConstant.ADDRESS_BOOK_IS_NULL);
    }

    // 3. 组装订单对象
    Orders order = new Orders();
    order.setNumber(generateOrderNumber());
    order.setStatus(Orders.PENDING_PAYMENT);        // 初始状态
    order.setPayStatus(Orders.UN_PAID);
    order.setUserId(userId);
    // ... 复制地址、金额等信息

    // 4. 插入订单
    orderMapper.insert(order);

    // 5. 插入订单明细（从购物车数据转换）
    List<OrderDetail> orderDetails = cartList.stream().map(cart -> {
        OrderDetail detail = new OrderDetail();
        BeanUtils.copyProperties(cart, detail);
        detail.setOrderId(order.getId());
        return detail;
    }).collect(Collectors.toList());
    orderDetailMapper.insertBatch(orderDetails);

    // 6. 清空购物车
    shoppingCartMapper.clear(userId);

    // 7. 返回结果
    return OrderSubmitVO.builder()
        .id(order.getId())
        .orderNumber(order.getNumber())
        .orderAmount(order.getAmount())
        .orderTime(order.getOrderTime())
        .build();
}
```

### 10.3 长事务问题

创建订单涉及多表操作（订单表、订单明细表、购物车表），要用 `@Transactional` 保证数据一致性：

```java
@Transactional(rollbackFor = Exception.class)
public OrderSubmitVO submit(OrdersSubmitDTO ordersSubmitDTO) {
    // 所有数据库操作要么全成功，要么全回滚
}
```

### 10.5 取消订单时的库存恢复

```java
public void cancel(Long orderId) {
    Orders order = orderMapper.getById(orderId);

    // 状态守卫
    if (order.getStatus().equals(Orders.COMPLETED)) {
        throw new OrderBusinessException("已完成订单无法取消");
    }

    // 更新订单状态
    order.setStatus(Orders.CANCELLED);
    order.setCancelTime(LocalDateTime.now());
    orderMapper.update(order);

    // 恢复库存
    List<OrderDetail> details = orderDetailMapper.getByOrderId(orderId);
    for (OrderDetail detail : details) {
        if (detail.getDishId() != null) {
            dishMapper.restoreStock(detail.getDishId(), detail.getNumber());
        }
        if (detail.getSetmealId() != null) {
            setmealMapper.restoreStock(detail.getSetmealId(), detail.getNumber());
        }
    }
}
```

## 11. 常见坑与最佳实践

### 11.1 坑1：状态用魔法数字

```java
// ❌ 坏代码：一个月后你还能记得 3 是什么意思吗？
order.setStatus(3);

// ✅ 好代码：用常量
order.setStatus(Orders.CONFIRMED);
```

### 11.2 坑2：忘记校验"终态不可变"

```java
// ❌ 没有终态检查
public void cancel(OrdersCancelDTO dto) {
    Orders order = orderMapper.getById(dto.getId());
    order.setStatus(CANCELLED);  // 已完成(5)的订单也能取消？
}

// ✅ 加上终态检查
public void cancel(OrdersCancelDTO dto) {
    Orders order = orderMapper.getById(dto.getId());
    if (order.getStatus().equals(Orders.COMPLETED)
        || order.getStatus().equals(Orders.CANCELLED)) {
        throw new OrderBusinessException("订单已结束，无法操作");
    }
    // ... 执行取消
}
```

### 11.3 坑3：并发操作导致状态错乱

多个请求同时操作同一个订单可能导致问题：

```
时间线：
  用户点击"取消" → 读到状态=2(待接单)
  商家点击"接单" → 读到状态=2(待接单)
  用户取消成功 → 状态变为6(已取消)
  商家接单成功 → 状态变为3(已接单)   ← 已取消的订单被接单了！
```

解决方案：

```java
// 方案1：乐观锁（推荐）
// 在 update SQL 中加上状态条件
UPDATE orders SET status = #{newStatus}
WHERE id = #{id} AND status = #{expectedStatus}
// 如果 affected rows = 0，说明状态已经被别人改了

// 方案2：悲观锁
SELECT * FROM orders WHERE id = #{id} FOR UPDATE
```

### 11.4 坑4：支付回调的幂等性

微信支付成功后会回调我们的接口，但这个回调可能**被重复调用**（网络重试）：

```java
// ✅ 处理支付回调时先检查状态
public void handlePaymentCallback(String orderNumber) {
    Orders order = orderMapper.getByNumber(orderNumber);

    // 幂等性：如果已经是"待接单"或之后的状态，说明已经处理过了
    if (!order.getStatus().equals(Orders.PENDING_PAYMENT)) {
        return;  // 已处理过，直接返回成功
    }

    // 更新状态
    order.setStatus(Orders.TO_BE_CONFIRMED);
    order.setPayStatus(Orders.PAID);
    orderMapper.update(order);
}
```

### 11.5 最佳实践总结

| 实践 | 说明 |
|------|------|
| **用常量不要用魔法数字** | `Orders.CONFIRMED` 而不是 `3` |
| **每个方法开头做状态守卫** | 先判断"当前状态是否允许这个操作" |
| **终态不可变** | COMPLETED(5) 和 CANCELLED(6) 不接受任何状态变更 |
| **注意并发安全** | 用乐观锁或悲观锁防止状态竞争 |
| **支付回调做幂等** | 同样的回调可能执行多次，要能正确处理 |
| **取消订单要恢复库存** | 否则会造成库存永久减少 |
| **记录状态变更时间** | cancelTime、checkoutTime、deliveryTime 等 |
| **大事务用 @Transactional** | 多表操作保证一致性 |

## 12. 总结

```
                    ┌─────────────────────────────┐
                    │     订单状态机核心概念        │
                    └─────────────────────────────┘
                                  │
            ┌─────────────────────┼─────────────────────┐
            │                     │                     │
            ▼                     ▼                     ▼
      ┌──────────┐        ┌──────────────┐       ┌──────────┐
      │  状态     │  ──→   │  事件(操作)   │ ──→  │  新状态   │
      │ (status)  │        │  (action)    │       │ (status)  │
      └──────────┘        └──────────────┘       └──────────┘
            │                     │                     │
            └─────────────────────┼─────────────────────┘
                                  │
                    每个操作前先检查：
                   "当前状态允许这个操作吗？"
```

**一句话总结：** 状态机就是给你的订单对象装上一套"交通规则"，明确规定了什么状态下能做什么操作、能去往哪个状态，防止出现"绿灯直接变红灯"或者"已取消订单还在配送"这样的逻辑错误。

**对你接下来的开发建议：**
1. 先实现主线流程：提交订单 → 支付 → 接单 → 派送 → 完成
2. 再补取消分支：各阶段取消 + 退款
3. 最后做查询和统计：历史订单、各状态统计

在学习项目中，用 if-else 做状态守卫就足够了，不必引入 Spring State Machine 等框架。关键是**养成"操作前先校验状态"的编码习惯**，这对以后做任何有状态流转的业务（审批流程、工单系统、支付系统等）都大有裨益。
